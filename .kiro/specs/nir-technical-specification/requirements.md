# Requirements Document: Техническое Задание (ТЗ) для проекта NowPlay

## Introduction

Данный документ описывает требования к созданию полного технического задания (ТЗ) в формате ГОСТ для проекта **"Разработка кроссплатформенной системы управления и визуализации мультимедийного контента для стриминговых сервисов"** (NowPlay). ТЗ должно быть максимально подробным и охватывать все аспекты проекта согласно стандартам ГОСТ 19.201-78 и ГОСТ 34.602-89, а также требованиям к выпускной квалификационной работе.

## Glossary

- **НИР** (Научно-Исследовательская Работа): Академический документ, описывающий исследование, разработку и результаты проекта
- **ТЗ** (Техническое Задание): Документ, определяющий требования, архитектуру и спецификации системы
- **NowPlay**: Десктопное приложение для отображения информации о текущем воспроизводимом треке в OBS Studio
- **MediaMonitor**: C# компонент для мониторинга медиаплееров через Windows Media Control API
- **WebSocket**: Протокол для двунаправленной связи в реальном времени
- **OBS Studio**: Программное обеспечение для стриминга и записи видео
- **Browser Source**: Источник в OBS Studio для отображения веб-контента
- **Ambient Light**: Подсветка обложки с автоматической цветовой палитрой
- **API** (Application Programming Interface): Интерфейс программирования приложений
- **GUI** (Graphical User Interface): Графический пользовательский интерфейс
- **CPU**: Центральный процессор
- **Canvas API**: JavaScript API для работы с графикой

## Requirements

### Requirement 1: Введение (Раздел 1)

**User Story:** Как автор ТЗ, я хочу создать раздел "Введение" с наименованием, областью применения и характеристикой программы, чтобы читатель понял назначение и контекст разработки системы NowPlay.

#### Acceptance Criteria

1. WHEN автор пишет подраздел "Наименование и область применения" THEN система SHALL указать полное наименование программы "NowPlay - система управления и визуализации мультимедийного контента для стриминговых сервисов"
2. WHEN автор описывает область применения THEN система SHALL указать целевую аудиторию (стримеры, контент-криейторы, пользователи OBS Studio) и сферу использования (стриминг на Twitch, YouTube, запись видео)
3. WHEN автор пишет краткую характеристику THEN система SHALL описать основное назначение программы как инструмент для автоматического отображения информации о текущем воспроизводимом треке в стриминговых приложениях
4. WHEN автор описывает ключевые возможности THEN система SHALL перечислить основные функции: автоматическое определение трека, получение обложек, настраиваемые шаблоны визуализации, извлечение цветов, интеграция с OBS
5. WHEN автор указывает технологическую платформу THEN система SHALL описать кроссплатформенную архитектуру с компонентами на Python и C#
6. WHEN автор описывает режимы работы THEN система SHALL указать основные режимы: desktop-приложение с GUI, веб-сервер с API, веб-виджеты для браузера
7. WHEN автор указывает целевую ОС THEN система SHALL указать Windows 10/11 как основную платформу с возможностью расширения на Linux и macOS

### Requirement 2: Основания для разработки (Раздел 2)

**User Story:** Как автор ТЗ, я хочу описать основания для разработки и цель проекта, чтобы обосновать необходимость создания системы NowPlay.

#### Acceptance Criteria

1. WHEN автор указывает документы-основания THEN система SHALL перечислить нормативные документы: ГОСТ 19.201-78, ГОСТ 34.602-89, требования к ВКР учебного заведения
2. WHEN автор описывает инициативу разработки THEN система SHALL указать, что разработка выполняется в рамках выпускной квалификационной работы
3. WHEN автор формулирует цель разработки THEN система SHALL четко сформулировать цель как "создание кроссплатформенной системы управления и визуализации мультимедийного контента для стриминговых сервисов с автоматическим отображением информации о текущем воспроизводимом треке"
4. WHEN автор описывает проблематику THEN система SHALL описать существующие ограничения текущих решений: высокая стоимость, ограниченная функциональность, отсутствие автоматического извлечения цветов, высокая нагрузка на CPU
5. WHEN автор обосновывает актуальность THEN система SHALL включить статистические данные о росте индустрии стриминга (количество стримеров на Twitch, YouTube Gaming)
6. WHEN автор описывает целевую аудиторию THEN система SHALL указать потребности стримеров и контент-криейторов в инструментах визуализации мультимедийного контента
7. WHEN автор формулирует ожидаемый результат THEN система SHALL описать создание функционального приложения с установщиком, документацией и результатами тестирования

### Requirement 3: Назначение разработки (Раздел 3)

**User Story:** Как автор ТЗ, я хочу описать функциональное и эксплуатационное назначение программы, чтобы определить область применения и предоставляемые сервисы системы NowPlay.

#### Acceptance Criteria

1. WHEN автор описывает функциональное назначение THEN система SHALL указать основную функцию: автоматическое отображение информации о текущем воспроизводимом мультимедийном контенте в стриминговых приложениях
2. WHEN автор описывает эксплуатационное назначение THEN система SHALL указать режимы использования: интеграция с OBS Studio через Browser Source, standalone веб-интерфейс, desktop-приложение для управления
3. WHEN автор перечисляет предоставляемые сервисы THEN система SHALL включить: мониторинг медиаплееров, получение метаданных трека, загрузка обложек альбомов, веб-сервер с API, визуализация треков, настройка внешнего вида
4. WHEN автор описывает сервис мониторинга THEN система SHALL указать поддержку Windows Media Control API с автоматическим определением текущего трека из любого медиаплеера
5. WHEN автор описывает сервис метаданных THEN система SHALL указать интеграцию с Last.fm, iTunes, Yandex Music, VK Music для получения информации о треках
6. WHEN автор описывает сервис визуализации THEN система SHALL указать наличие 4 настраиваемых шаблонов с поддержкой автоматического извлечения цветов из обложек
7. WHEN автор описывает целевых пользователей THEN система SHALL указать стримеров на Twitch/YouTube, контент-криейторов, пользователей OBS Studio/Streamlabs

### Requirement 4: Требования к программе - Функциональные характеристики (Раздел 4.1)

**User Story:** Как автор ТЗ, я хочу детально описать функциональные требования к программе, чтобы определить все необходимые возможности системы NowPlay.

#### Acceptance Criteria

1. WHEN автор описывает мониторинг медиаплееров THEN система SHALL указать требование автоматического определения текущего трека через Windows Media Control API с частотой опроса 1 секунда
2. WHEN автор описывает получение метаданных THEN система SHALL указать требование извлечения информации: исполнитель, название трека, альбом, длительность, текущая позиция воспроизведения, статус (играет/пауза)
3. WHEN автор описывает получение обложек THEN система SHALL указать требование автоматической загрузки обложек из источников (Last.fm, iTunes, Yandex Music, VK Music) с приоритизацией и fallback-механизмами
4. WHEN автор описывает веб-сервер THEN система SHALL указать требование HTTP сервера на порту 80 с endpoints: POST /update_from_cs, GET /cover, GET /ws, POST /update_config, GET /sources
5. WHEN автор описывает визуализацию THEN система SHALL указать требование 4 шаблонов (вертикальный, альтернативный, минималистичный, горизонтальный) с настраиваемыми параметрами
6. WHEN автор описывает настройку внешнего вида THEN система SHALL указать требование настройки цветов (фон, акцент, текст, волна, прогресс-бар), позиционирования, параметров визуализатора, ambient light
7. WHEN автор описывает GUI THEN система SHALL указать требование desktop-приложения с тремя страницами (Start, Settings, Info), боковым меню навигации, индикаторами статуса
8. WHEN автор описывает интеграцию C# и Python THEN система SHALL указать требование взаимодействия через HTTP POST с передачей JSON данных о треке
9. WHEN автор описывает управление конфигурацией THEN система SHALL указать требование сохранения настроек в config.json с автоматической перезагрузкой при изменении

### Requirement 5: Требования к программе - Надёжность (Раздел 4.2)

**User Story:** Как автор ТЗ, я хочу определить требования к надёжности системы, чтобы обеспечить стабильную работу в различных условиях.

#### Acceptance Criteria

1. WHEN автор описывает обработку ошибок подключения THEN система SHALL указать требование корректной обработки отсутствия активных медиаплееров с отображением статуса "inactive"
2. WHEN автор описывает стабильность веб-сервера THEN система SHALL указать требование непрерывной работы сервера минимум 24 часа без перезапуска с автоматическим восстановлением после ошибок
3. WHEN автор описывает надёжность получения обложек THEN система SHALL указать требование fallback-механизма при недоступности источника с переключением на альтернативный источник
4. WHEN автор описывает синхронизацию компонентов THEN система SHALL указать требование автоматического переподключения C# компонента к Python серверу при разрыве соединения
5. WHEN автор описывает обработку некорректных данных THEN система SHALL указать требование валидации входных данных с отклонением некорректных запросов
6. WHEN автор описывает управление памятью THEN система SHALL указать требование отсутствия утечек памяти при длительной работе (24+ часа)
7. WHEN автор описывает логирование ошибок THEN система SHALL указать требование записи критических ошибок в лог-файл для диагностики

### Requirement 6: Требования к программе - Производительность (Раздел 4.3)

**User Story:** Как автор ТЗ, я хочу определить требования к производительности системы, чтобы обеспечить эффективное использование ресурсов.

#### Acceptance Criteria

1. WHEN автор описывает время реакции THEN система SHALL указать требование обнаружения смены трека не более чем за 2 секунды с момента переключения
2. WHEN автор описывает загрузку обложек THEN система SHALL указать требование загрузки обложки не более чем за 3 секунды при наличии интернет-соединения
3. WHEN автор описывает нагрузку CPU THEN система SHALL указать требование нагрузки не более 2% CPU при переключении треков и не более 0.5% в режиме ожидания
4. WHEN автор описывает использование памяти THEN система SHALL указать требование использования не более 150 МБ RAM для Python компонента и не более 50 МБ для C# компонента
5. WHEN автор описывает троттлинг THEN система SHALL указать требование минимального интервала 100ms между WebSocket обновлениями для предотвращения перегрузки клиентов
6. WHEN автор описывает время запуска THEN система SHALL указать требование запуска desktop-приложения не более чем за 5 секунд
7. WHEN автор описывает задержку обновлений THEN система SHALL указать требование задержки обновления веб-виджета не более 500ms после получения данных сервером

### Requirement 7: Требования к программе - Технические средства (Раздел 4.4)

**User Story:** Как автор ТЗ, я хочу определить требования к техническим средствам, чтобы указать минимальные и рекомендуемые характеристики оборудования.

#### Acceptance Criteria

1. WHEN автор описывает минимальные требования к ОС THEN система SHALL указать Windows 10 (64-bit) или выше
2. WHEN автор описывает минимальные требования к процессору THEN система SHALL указать Intel Core i3 или AMD Ryzen 3 (2 ядра, 2.0 GHz)
3. WHEN автор описывает минимальные требования к памяти THEN система SHALL указать 4 ГБ RAM
4. WHEN автор описывает минимальные требования к диску THEN система SHALL указать 500 МБ свободного места на жестком диске
5. WHEN автор описывает рекомендуемые требования THEN система SHALL указать Windows 11, Intel Core i5/AMD Ryzen 5 (4 ядра, 3.0 GHz), 8 ГБ RAM, 1 ГБ свободного места
6. WHEN автор описывает требования к сети THEN система SHALL указать подключение к интернету для получения обложек (минимум 1 Мбит/с)
7. WHEN автор описывает дополнительное ПО THEN система SHALL указать .NET 6.0 Runtime для C# компонента, Python 3.12+ для запуска из исходников

### Requirement 8: Требования к программе - Совместимость (Раздел 4.5)

**User Story:** Как автор ТЗ, я хочу определить требования к информационной и программной совместимости, чтобы обеспечить интеграцию с различными системами.

#### Acceptance Criteria

1. WHEN автор описывает совместимость с медиаплеерами THEN система SHALL указать поддержку всех медиаплееров, использующих Windows Media Control API (Spotify, VLC, Windows Media Player, Groove Music, Chrome, Firefox)
2. WHEN автор описывает программную совместимость THEN система SHALL указать совместимость с Python 3.12+, .NET 6.0+, aiohttp 3.8+, CustomTkinter 5.0+
3. WHEN автор описывает совместимость с OBS THEN система SHALL указать поддержку OBS Studio 28.0+ и Streamlabs OBS через Browser Source
4. WHEN автор описывает информационную совместимость THEN система SHALL указать форматы данных: JSON для API, PNG для обложек, HTML/CSS/JavaScript для виджетов
5. WHEN автор описывает среду выполнения THEN система SHALL указать требование Windows 10/11 с установленными .NET 6.0 Runtime и Python 3.12+ (для запуска из исходников)
6. WHEN автор описывает протоколы THEN система SHALL указать использование HTTP/1.1, WebSocket (RFC 6455), JSON (RFC 8259)
7. WHEN автор описывает кодировки THEN система SHALL указать UTF-8 для всех текстовых данных

### Requirement 9: Требования к программе - Эргономика и эстетика (Раздел 4.6)

**User Story:** Как автор ТЗ, я хочу определить требования к эргономике и технической эстетике, чтобы обеспечить удобство использования и привлекательный внешний вид.

#### Acceptance Criteria

1. WHEN автор описывает структуру GUI THEN система SHALL указать требование боковой панели навигации с иконками и текстовыми метками, трех основных страниц (Start, Settings, Info)
2. WHEN автор описывает требования к веб-виджетам THEN система SHALL указать требование адаптивного дизайна, плавных анимаций (transition 0.3s), читаемых шрифтов (минимум 14px)
3. WHEN автор описывает UX-принципы THEN система SHALL указать требование минимального количества кликов для основных действий (запуск сервера - 1 клик, смена шаблона - 2 клика)
4. WHEN автор описывает визуальную обратную связь THEN система SHALL указать требование индикации статуса (зеленый - активен, красный - неактивен), анимации при загрузке, уведомлений об ошибках
5. WHEN автор описывает цветовую схему THEN система SHALL указать требование темной темы по умолчанию с возможностью настройки акцентных цветов
6. WHEN автор описывает доступность THEN система SHALL указать требование контрастности текста минимум 4.5:1, размер кликабельных элементов минимум 44x44px
7. WHEN автор описывает консистентность THEN система SHALL указать требование единообразного стиля кнопок, полей ввода, выпадающих списков во всем приложении

### Requirement 10: Требования к программе - Эксплуатация (Раздел 4.7)

**User Story:** Как автор ТЗ, я хочу определить требования к эксплуатации системы, чтобы описать порядок установки, запуска и обслуживания.

#### Acceptance Criteria

1. WHEN автор описывает порядок установки THEN система SHALL указать два варианта: установка из готового установщика (NowPlay-Setup.exe) и запуск из исходников (python main.py)
2. WHEN автор описывает порядок запуска THEN система SHALL указать последовательность: запуск desktop-приложения, нажатие кнопки START, копирование ссылки, добавление Browser Source в OBS
3. WHEN автор описывает режимы работы THEN система SHALL указать три режима: только Python мониторинг (use_builtin_monitor: true), только C# мониторинг (рекомендуется), гибридный режим (для отладки)
4. WHEN автор описывает автоматический запуск THEN система SHALL указать возможность использования start_media_monitor.bat для одновременного запуска обоих компонентов
5. WHEN автор описывает обслуживание THEN система SHALL указать требование периодической очистки кэша обложек (папка songinfo), проверки обновлений зависимостей
6. WHEN автор описывает остановку THEN система SHALL указать корректное завершение через кнопку STOP в GUI или закрытие окна приложения
7. WHEN автор описывает резервное копирование THEN система SHALL указать необходимость сохранения файла config.json для восстановления настроек

### Requirement 11: Требования к программе - Защита информации (Раздел 4.8)

**User Story:** Как автор ТЗ, я хочу определить требования к защите информации, чтобы обеспечить безопасность данных пользователей.

#### Acceptance Criteria

1. WHEN автор описывает сетевую безопасность THEN система SHALL указать требование работы только на localhost (127.0.0.1) без внешнего доступа
2. WHEN автор описывает конфиденциальность THEN система SHALL указать, что система не собирает и не передает персональные данные пользователей третьим лицам
3. WHEN автор описывает безопасность API THEN система SHALL указать требование валидации входных данных для предотвращения инъекций
4. WHEN автор описывает хранение данных THEN система SHALL указать, что обложки и конфигурация хранятся локально без передачи в облако
5. WHEN автор описывает внешние запросы THEN система SHALL указать, что запросы к API источников обложек (Last.fm, iTunes) выполняются только при необходимости
6. WHEN автор описывает логирование THEN система SHALL указать, что логи не содержат чувствительной информации (пароли, токены)
7. WHEN автор описывает обновления THEN система SHALL указать рекомендацию регулярного обновления зависимостей для устранения уязвимостей

### Requirement 12: Требования к документированию (Раздел 5)

**User Story:** Как автор ТЗ, я хочу определить требования к документации системы, чтобы обеспечить полноту и качество сопроводительных материалов.

#### Acceptance Criteria

1. WHEN автор перечисляет документацию THEN система SHALL указать: руководство пользователя, техническая документация, документация для разработчиков, README файлы, комментарии в коде
