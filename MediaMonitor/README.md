# MediaMonitor - C# интеграция с Python сервером

## Описание

MediaMonitor - это C# приложение, которое отслеживает текущее воспроизведение медиа в Windows (через Windows Media Control API) и отправляет данные на Python сервер now.py. Система включает автоматическое восстановление при сбоях, мониторинг здоровья подписок на события и изоляцию компонентов для обеспечения непрерывной работы.

## Функциональность

- ✅ Отслеживание текущего трека (исполнитель, название)
- ✅ Получение обложки альбома
- ✅ Отслеживание позиции воспроизведения и длительности
- ✅ Определение статуса воспроизведения (играет/пауза)
- ✅ Автоматическая отправка данных на Python сервер через HTTP API
- ✅ Автоматическое восстановление при сбоях подписок на события
- ✅ Мониторинг здоровья системы с обнаружением таймаутов
- ✅ Защита от взаимоблокировок (deadlock) с таймаутами блокировок
- ✅ Изоляция опроса конфигурации от основного цикла событий
- ✅ Диагностический режим с подробным логированием

### Компоненты

1. **MediaMonitor.cs** - основной класс-координатор, который:
   - Инициализирует и координирует все компоненты
   - Подключается к Windows Media Control API
   - Управляет жизненным циклом приложения

2. **HealthMonitor.cs** - мониторинг здоровья системы:
   - Проверяет получение обновлений каждые 5 секунд
   - Обнаруживает таймауты (30 секунд без обновлений)
   - Инициирует процедуру восстановления при необходимости

3. **RecoveryManager.cs** - автоматическое восстановление:
   - Отписывается от всех текущих событий
   - Переинициализирует Session Manager
   - Восстанавливает подписки на события
   - Ограничивает количество попыток восстановления (максимум 3)

4. **EventSubscriptionManager.cs** - управление подписками на события:
   - Централизует управление подписками WinRT
   - Логирует все вызовы обработчиков событий
   - Отслеживает время выполнения обработчиков
   - Обеспечивает корректную очистку при отписке

5. **UpdateQueue.cs** - очередь обновлений с защитой от взаимоблокировок:
   - Группирует обновления (debounce) для снижения частоты HTTP запросов
   - Использует таймауты при захвате блокировок (5 секунд)
   - Пропускает обновления при невозможности захвата блокировки
   - Инициирует восстановление при повторяющихся таймаутах

6. **HttpClientPool.cs** - пул HTTP клиентов с логикой повторов:
   - Управляет HTTP запросами с таймаутами (5 секунд)
   - Реализует экспоненциальную задержку при повторах (100ms, 500ms, 1000ms)
   - Гарантирует освобождение семафора во всех сценариях
   - Логирует все HTTP запросы с информацией о времени выполнения

7. **IsolatedConfigPoller.cs** - изолированный опрос конфигурации:
   - Использует отдельный экземпляр HttpClient
   - Ставит изменения в очередь вместо блокировки
   - Применяет debounce к быстрым изменениям (минимум 2 секунды)
   - Изолирует ошибки от основного цикла событий

8. **DiagnosticLogger.cs** - система диагностического логирования:
   - Записывает события с временными метками
   - Отслеживает длительность операций
   - Создает файлы логов в режиме диагностики
   - Форматирует вывод для удобства чтения

9. **CoverFetcher.cs** - загрузка и сохранение обложек альбомов

10. **CurrentMediaState.cs** - модель данных о текущем треке

11. **Python сервер (now.py)** - принимает данные через endpoint `/update_from_cs` и рассылает их всем подключенным WebSocket клиентам

## Запуск

### 1. Запустите Python сервер

```bash
python main.py
```

Сервер запустится на `http://localhost:58080`

### 2. Соберите и запустите C# приложение

```bash
cd MediaMonitor
dotnet build
dotnet run
```

Или откройте `MediaMonitor.sln` в Visual Studio и запустите проект.

### 3. Диагностический режим (опционально)

Для включения подробного логирования запустите с флагом `--diagnostic`:

```bash
dotnet run -- --diagnostic
```

или

```bash
MediaMonitor.exe --diagnostic
```

В диагностическом режиме:
- Все события логируются с точными временными метками
- Создается файл лога в директории `logs/`
- Отслеживаются все подписки на события, HTTP запросы и процедуры восстановления
- Логируются все операции захвата/освобождения блокировок
- Записывается информация о времени выполнения каждой операции

Подробнее см. [DIAGNOSTIC_MODE.md](DIAGNOSTIC_MODE.md)

## Автоматическое восстановление

MediaMonitor включает систему автоматического восстановления для обеспечения непрерывной работы:

### Обнаружение проблем

**HealthMonitor** непрерывно отслеживает поток обновлений:
- Проверяет наличие обновлений каждые 5 секунд
- Обнаруживает таймауты, если обновления не получены в течение 30 секунд
- Автоматически инициирует процедуру восстановления

### Процедура восстановления

Когда обнаружен таймаут, **RecoveryManager** выполняет следующие шаги:

1. **Отписка от событий**: Отписывается от всех текущих обработчиков событий WinRT
2. **Переинициализация**: Пересоздает GlobalSystemMediaTransportControlsSessionManager
3. **Восстановление подписок**: Заново подписывается на все события медиа
4. **Верификация**: Проверяет успешность восстановления, ожидая обновление в течение 10 секунд
5. **Логирование**: Записывает результат восстановления (успех/неудача)

### Ограничения восстановления

- Максимум 3 попытки восстановления подряд
- После 3 неудачных попыток система переходит в режим деградации
- Требуется ручной перезапуск приложения

### Логирование восстановления

Все процедуры восстановления логируются:
```
[2024-12-08 19:30:45] RECOVERY: Initiating recovery procedure (attempt 1/3)
[2024-12-08 19:30:45] RECOVERY: Unsubscribing from all events
[2024-12-08 19:30:45] RECOVERY: Reinitializing session manager
[2024-12-08 19:30:46] RECOVERY: Reestablishing event subscriptions
[2024-12-08 19:30:46] RECOVERY: Recovery completed successfully
```

## Защита от взаимоблокировок

Система включает несколько механизмов защиты от взаимоблокировок (deadlock):

### Таймауты блокировок

**UpdateQueue** использует таймауты при захвате блокировок:
- Таймаут 5 секунд для захвата блокировки обновлений
- Пропускает обновление, если блокировка недоступна
- Логирует все таймауты для диагностики
- Инициирует восстановление при повторяющихся таймаутах

### Таймауты HTTP семафора

**HttpClientPool** защищает от блокировки HTTP запросов:
- Таймаут 3 секунды для захвата семафора HTTP
- Таймаут 5 секунд для выполнения HTTP запроса
- Гарантирует освобождение семафора в блоке `finally`
- Реализует повторы с экспоненциальной задержкой

### Изоляция ConfigPoller

**IsolatedConfigPoller** изолирован от основного цикла:
- Использует отдельный экземпляр HttpClient
- Ошибки не распространяются на обработку событий медиа
- Изменения ставятся в очередь без блокировки
- Применяется debounce для предотвращения частых изменений

## Устранение неполадок

### Проблема: Обновления треков прекращаются

**Симптомы:**
- Медиа воспроизводится в Windows, но обновления не приходят
- Python сервер не получает новые данные
- Последнее обновление было более 30 секунд назад

**Решение:**
1. Проверьте логи на наличие сообщений о восстановлении:
   ```
   RECOVERY: Initiating recovery procedure
   ```
2. Если автоматическое восстановление не помогло, перезапустите MediaMonitor
3. Запустите в диагностическом режиме для детального анализа:
   ```bash
   MediaMonitor.exe --diagnostic
   ```
4. Проверьте файл лога в `logs/` на наличие ошибок подписки на события

### Проблема: Высокая загрузка CPU

**Симптомы:**
- MediaMonitor потребляет много CPU
- Система работает медленно

**Решение:**
1. Проверьте логи на наличие повторяющихся таймаутов блокировок
2. Проверьте, не происходят ли слишком частые изменения медиа
3. Убедитесь, что Python сервер отвечает на HTTP запросы
4. Проверьте сетевое подключение к серверу

### Проблема: HTTP запросы не доходят до сервера

**Симптомы:**
- MediaMonitor работает, но Python сервер не получает обновления
- В логах видны ошибки HTTP запросов

**Решение:**
1. Убедитесь, что Python сервер запущен и доступен
2. Проверьте URL сервера в конфигурации MediaMonitor
3. Проверьте, не блокирует ли брандмауэр соединение
4. Проверьте логи на наличие таймаутов HTTP:
   ```
   HTTP: Request timeout after 5000ms
   ```
5. Система автоматически повторит запросы с экспоненциальной задержкой

### Проблема: Утечки памяти

**Симптомы:**
- Использование памяти MediaMonitor постоянно растет
- Система замедляется со временем

**Решение:**
1. Убедитесь, что используется последняя версия с автоматическим восстановлением
2. Проверьте, что все подписки на события корректно отписываются
3. Запустите в диагностическом режиме и отслеживайте количество активных подписок
4. Если проблема сохраняется, перезапустите приложение

### Проблема: ConfigPoller блокирует обновления медиа

**Симптомы:**
- Обновления медиа задерживаются
- В логах видны ошибки ConfigPoller

**Решение:**
1. Проверьте, что ConfigPoller использует изолированный HTTP клиент
2. Убедитесь, что ошибки ConfigPoller не распространяются на основной цикл
3. Проверьте доступность конфигурационного endpoint
4. ConfigPoller автоматически изолирован и не должен влиять на медиа обновления

### Проблема: Восстановление не срабатывает

**Симптомы:**
- Обновления прекратились более 30 секунд назад
- В логах нет сообщений о восстановлении

**Решение:**
1. Проверьте, что HealthMonitor запущен (должен быть в логах при старте)
2. Убедитесь, что heartbeat таймер работает (проверка каждые 5 секунд)
3. Проверьте, не достигнут ли лимит попыток восстановления (3 попытки)
4. Если лимит достигнут, требуется ручной перезапуск

### Проблема: Слишком частые восстановления

**Симптомы:**
- Процедура восстановления запускается слишком часто
- В логах много сообщений RECOVERY

**Решение:**
1. Проверьте стабильность Windows Media API (возможно, проблема в системе)
2. Убедитесь, что медиа-приложения работают корректно
3. Проверьте, не конфликтуют ли другие приложения с Media API
4. Попробуйте перезапустить медиа-приложение (Spotify, iTunes и т.д.)

## Диагностика и мониторинг

### Включение диагностического режима

Запустите с флагом `--diagnostic` для подробного логирования:

```bash
MediaMonitor.exe --diagnostic
```

### Что логируется в диагностическом режиме

1. **События подписки:**
   ```
   [EVENT] MediaPropertiesChanged fired at 19:30:45.123
   [EVENT] Handler execution took 15ms
   ```

2. **HTTP запросы:**
   ```
   [HTTP] Sending update to http://localhost:58080/update_from_cs
   [HTTP] Request completed in 45ms (success)
   ```

3. **Операции с блокировками:**
   ```
   [LOCK] Acquiring update lock...
   [LOCK] Lock acquired in 2ms
   [LOCK] Lock released
   ```

4. **Процедуры восстановления:**
   ```
   [RECOVERY] Initiating recovery procedure (attempt 1/3)
   [RECOVERY] Recovery completed successfully
   ```

5. **Мониторинг здоровья:**
   ```
   [HEALTH] Heartbeat check: Last update 3 seconds ago (healthy)
   [HEALTH] Timeout detected: No updates for 30 seconds
   ```

### Файлы логов

Логи сохраняются в директории `logs/`:
- `mediamonitor_YYYYMMDD_HHMMSS.log` - основной лог-файл
- Новый файл создается при каждом запуске в диагностическом режиме
- Логи включают временные метки с точностью до миллисекунд

## API компонентов

### HealthMonitor

```csharp
public class HealthMonitor
{
    // События
    public event EventHandler<HealthStatusEventArgs> HealthStatusChanged;

    public void RecordUpdate();  // Записать получение обновления

    public void Stop();          // Остановить мониторинг
}
```

### RecoveryManager

```csharp
public class RecoveryManager
{
    // Методы
    public async Task<bool> AttemptRecovery();  // Попытка восстановления
    public void ResetAttempts();                // Сброс счетчика попыток
}
```

### EventSubscriptionManager

```csharp
public class EventSubscriptionManager
{
    // События
    public event EventHandler<MediaUpdateEventArgs> MediaUpdated;
```

```csharp
public class UpdateQueue
```
