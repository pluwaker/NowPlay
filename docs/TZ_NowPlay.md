# ТЕХНИЧЕСКОЕ ЗАДАНИЕ

## Проект: "Разработка системы управления и визуализации мультимедийного контента для стриминговых сервисов"

**Наименование программы:** NowPlay  
**Версия документа:** 2.0  
**Дата:** Декабрь 2024

---

## 1. Введение

### 1.1 Наименование и область применения

Данный раздел определяет официальное наименование разрабатываемого программного обеспечения, описывает целевую аудиторию и сферу применения системы, а также устанавливает требования к операционной системе. Информация, представленная в этом разделе, позволяет четко идентифицировать программный продукт и понять, для каких пользователей и задач он предназначен.

**Полное наименование программы:**  
NowPlay — система управления и визуализации мультимедийного контента для стриминговых сервисов

**Назначение:**  
Программа предназначена для автоматического отображения информации о текущем воспроизводимом музыкальном треке непосредственно в прямых трансляциях и видеозаписях. Система решает задачу информирования зрителей о музыкальном контенте без необходимости ручного ввода данных стримером.

**Целевая аудитория:**  
Программа ориентирована на широкий круг пользователей, работающих с мультимедийным контентом. Основную аудиторию составляют стримеры на платформах Twitch и YouTube Gaming (как профессиональные, так и начинающие), контент-криейторы, создающие видеоконтент для различных платформ, пользователи программного обеспечения для стриминга (OBS Studio, Streamlabs OBS), музыкальные блогеры и обозреватели, создатели подкастов и аудиоконтента, а также разработчики, желающие расширить функциональность системы.

**Область применения:**  
Система применяется в следующих сценариях: прямые трансляции на платформах Twitch, YouTube Gaming, Facebook Gaming; запись видеоконтента с отображением информации о воспроизводимой музыке; создание музыкальных шоу и подкастов; интеграция музыкального контента в игровые стримы; профессиональное оформление трансляций и видеозаписей.

**Целевая операционная система:**  
Основной платформой является Windows 10 (64-bit) версии 1903 (May 2019 Update) и выше, а также Windows 11. Выбор Windows в качестве основной платформы обусловлен широким распространением этой операционной системы среди стримеров и наличием Windows Media Control API для мониторинга медиаплееров. Архитектура системы спроектирована с учетом будущей кроссплатформенности и предусматривает поддержку Linux (через MPRIS D-Bus API) и macOS (через MediaPlayer framework).

### 1.2 Краткая характеристика области применения программы

В данном разделе представлена общая характеристика разрабатываемой системы, описаны основные принципы её работы, технологическая платформа и ключевые функциональные возможности. Раздел позволяет получить целостное представление о программном продукте, понять его архитектуру и оценить технические характеристики системы.

**Основное назначение:**  
NowPlay представляет собой комплексное решение для автоматического отображения информации о текущем воспроизводимом мультимедийном контенте в стриминговых приложениях. Программа работает полностью автоматически, не требуя вмешательства пользователя после первоначальной настройки, что позволяет стримеру сосредоточиться на создании контента.

**Принцип работы:**  
Система осуществляет непрерывный мониторинг активных медиаплееров на компьютере пользователя через Windows Media Control API с частотой опроса один раз в секунду. При обнаружении воспроизведения музыки программа автоматически извлекает метаданные трека (исполнитель, название, альбом, длительность, текущая позиция воспроизведения) и инициирует загрузку обложки альбома из множественных источников с интеллектуальной приоритизацией.

Поддерживаются все популярные медиаплееры и стриминговые сервисы: Spotify, Apple Music, YouTube Music, VLC Media Player, Windows Media Player, Groove Music, а также веб-браузеры (Chrome, Firefox, Edge, Opera) при воспроизведении музыки на веб-сайтах.

**Получение обложек:**  
Система использует иерархию источников для загрузки обложек альбомов: Windows Media Thumbnail API (получение непосредственно от медиаплеера), Last.fm API (обширная база западной музыки), iTunes Search API (официальный каталог Apple Music с высоким качеством изображений), Yandex Music API (специализация на русскоязычной музыке), VK Music API (дополнительный источник для локального контента). При недоступности одного источника система автоматически переключается на следующий, обеспечивая максимальную доступность обложек.

**Визуализация:**  
Информация отображается через настраиваемые веб-виджеты, интегрируемые в OBS Studio через Browser Source. Предоставляется четыре профессиональных шаблона визуализации, оптимизированных для различных сценариев: вертикальный (300x400 пикселей, классический формат для углов экрана), альтернативный (350x350 пикселей, модернизированная версия с акцентом на типографику), минималистичный (250x80 пикселей, ультра-компактный для игровых стримов), горизонтальный (600x120 пикселей, широкий формат для размещения внизу экрана).

Все шаблоны поддерживают автоматическое извлечение доминирующих цветов из обложки альбома для создания гармоничной цветовой палитры, Ambient Light эффект (динамическая подсветка вокруг обложки), плавные CSS анимации и transitions, прозрачный фон для наложения на любой контент.

**Технологическая платформа:**  
Система построена на гибридной архитектуре, объединяющей преимущества различных технологий. Backend реализован на Python 3.12+ с использованием асинхронного веб-сервера aiohttp 3.8+ для обработки HTTP запросов и WebSocket соединений, библиотеки CustomTkinter 5.0+ для создания современного графического интерфейса и JSON-based config manager для управления конфигурацией.

Компонент мониторинга медиаплееров разработан на C# .NET 6.0+ с использованием Windows Media Control API, что обеспечивает высокую производительность, низкую задержку и нативную интеграцию с операционной системой Windows. Frontend построен на стандартных веб-технологиях HTML5/CSS3/JavaScript с применением Canvas API для обработки изображений и извлечения цветов, WebSocket API для real-time обновлений без задержек.

**Производительность:**  
Система оптимизирована для минимальной нагрузки на системные ресурсы: нагрузка на CPU составляет менее 2% при активном переключении треков и менее 0.5% в режиме ожидания, использование оперативной памяти не превышает 200 МБ (Python компонент менее 150 МБ, C# компонент менее 50 МБ), время реакции на смену трека составляет менее 2 секунд, система обеспечивает стабильную работу 24+ часа без перезапуска и деградации производительности.

### 2.2 Цель разработки

Данный раздел обосновывает необходимость создания системы NowPlay, анализирует существующие решения на рынке и их недостатки, подтверждает актуальность разработки статистическими данными индустрии стриминга, а также формулирует ожидаемые результаты проекта. Представленный анализ демонстрирует, что разработка нового программного продукта является обоснованной и востребованной.

Целью разработки является создание кроссплатформенной системы управления и визуализации мультимедийного контента для стриминговых сервисов с автоматическим отображением информации о текущем воспроизводимом треке, обеспечивающей высокую производительность, гибкую настройку визуализации и бесшовную интеграцию с популярными стриминговыми приложениями.

**Анализ существующих решений:**

Анализ рынка программного обеспечения для отображения информации о музыке в стримах выявил ряд существенных проблем. Коммерческие решения (Streamlabs Ultra за $19/месяц или $228/год, XSplit Broadcaster Premium за $25/месяц или $300/год, Pretzel Rocks Pro за $15/месяц или $180/год) требуют значительных финансовых затрат, что создает барьер для начинающих стримеров и студентов. Бесплатные альтернативы обладают ограниченной функциональностью: Snip поддерживает только Spotify без визуализации обложек, OBS Now Playing имеет базовый функционал без настройки внешнего вида.

Серьезной проблемой является высокая нагрузка на системные ресурсы. Многие программы используют неоптимизированные алгоритмы обработки изображений, что приводит к нагрузке на CPU в диапазоне 15-35% при обработке обложек и избыточному использованию оперативной памяти (более 300 МБ). Это негативно влияет на производительность стриминга и игр. Большинство решений работают только на Windows, ограничивая пользователей других операционных систем.

Дополнительную сложность создает ограниченная поддержка источников метаданных. Многие решения зависят от единственного API (Last.fm или Spotify) без fallback-механизмов, что приводит к проблемам с получением обложек для локальных файлов и отсутствию поддержки региональных сервисов (Yandex Music, VK Music).

**Актуальность разработки:**

Индустрия стриминга демонстрирует динамичный рост. По данным Twitch Tracker (2024), на платформе Twitch зарегистрировано более 9.5 миллионов активных стримеров, YouTube Gaming насчитывает более 40 миллионов игровых каналов. Среднее количество одновременных зрителей на Twitch превышает 2.5 миллиона человек, рынок стримингового оборудования и ПО оценивается в $4.3 миллиарда.

Музыкальный контент играет ключевую роль: 78% стримеров используют фоновую музыку во время трансляций, 65% зрителей отмечают важность качественного аудиосопровождения. Интеграция музыки повышает вовлеченность аудитории на 23%. Спрос на инструменты визуализации подтверждается тем, что 89% профессиональных стримеров используют кастомные оверлеи и виджеты, а запросы на бесплатные альтернативы растут на 35% ежегодно.

**Ожидаемый результат:**

Разработка NowPlay предоставит стримерам и контент-криейторам бесплатное, высокопроизводительное и функциональное решение с открытым исходным кодом, устраняя основные недостатки существующих аналогов. Система будет обеспечивать минимальную нагрузку на ресурсы (менее 2% CPU, менее 200 МБ памяти), поддержку множества медиаплееров и источников обложек, гибкую настройку визуализации и простую интеграцию с OBS Studio.

## 3. Назначение разработки

### 3.1 Функциональное и эксплуатационное назначение программы

В данном разделе раскрывается функциональное назначение программы NowPlay, описываются основные задачи, которые решает система, и детально характеризуются режимы её эксплуатации. Раздел позволяет понять, какие функции выполняет программа, как она используется в различных сценариях работы и какие возможности предоставляет пользователям.

**Функциональное назначение:**

Основной функцией программы NowPlay является автоматическое отображение информации о текущем воспроизводимом мультимедийном контенте в стриминговых приложениях и видеозаписях. Система осуществляет непрерывный мониторинг активных медиаплееров на компьютере пользователя, извлекает метаданные о воспроизводимых треках и автоматически загружает обложки альбомов из множественных источников, предоставляя визуальное представление этой информации через настраиваемые веб-виджеты.

Программа решает задачу информирования зрителей о музыкальном контенте, звучащем во время трансляции или в записанном видео, без необходимости ручного ввода данных стримером. Это позволяет зрителям узнавать названия понравившихся треков, повышает профессионализм оформления контента и улучшает взаимодействие между стримером и аудиторией. Система работает полностью автоматически, не требуя вмешательства пользователя после первоначальной настройки.

**Эксплуатационное назначение:**

Программа NowPlay предназначена для эксплуатации в трех основных режимах использования, каждый из которых ориентирован на определенные сценарии применения и категории пользователей.

Первый режим — интеграция с OBS Studio через Browser Source — является основным режимом работы для стримеров и контент-криейторов. Веб-виджет добавляется в сцену OBS как источник Browser Source, обеспечивая отображение информации о текущем треке непосредственно в трансляции. Процесс интеграции максимально упрощен и требует минимальных действий от пользователя.

Второй режим — standalone веб-интерфейс — предназначен для тестирования и предварительного просмотра виджетов перед добавлением в OBS, использования на втором мониторе для личного контроля воспроизводимой музыки, а также для разработки и отладки новых шаблонов визуализации.

Третий режим — desktop-приложение с графическим интерфейсом — является центром управления всей системой, предоставляя интуитивный интерфейс для конфигурации, управления сервером и настройки параметров визуализации.

### 3.2 Краткое описание предоставляемых сервисов

Данный раздел описывает комплекс взаимосвязанных сервисов, которые предоставляет система NowPlay для обеспечения полного цикла обработки мультимедийной информации — от мониторинга медиаплееров до визуализации данных в стриминговых приложениях. Каждый сервис выполняет специализированную функцию и взаимодействует с другими компонентами через четко определенные интерфейсы.

**Сервис мониторинга медиаплееров:**

Система предоставляет сервис автоматического мониторинга активных медиаплееров через Windows Media Control API с частотой опроса один раз в секунду. Сервис обеспечивает обнаружение воспроизведения музыки, извлечение базовых метаданных непосредственно от медиаплеера и автоматическую инициацию загрузки обложки при смене трека.

**Сервис получения метаданных и обложек:**

Предоставляется сервис получения полных метаданных треков и загрузки обложек альбомов с интеллектуальной приоритизацией источников и fallback-механизмами. Система использует иерархию источников (Windows Media Thumbnail API, Last.fm, iTunes, Yandex Music, VK Music) для обеспечения максимальной доступности обложек.

**Веб-сервер с API:**

Встроенный асинхронный веб-сервер предоставляет RESTful API и WebSocket для real-time обновлений. Сервер работает на localhost, обеспечивая безопасность, и предоставляет endpoints для получения информации о текущем треке, обложки, обновления конфигурации и установки WebSocket соединений.

**Сервис визуализации:**

Система предоставляет четыре профессиональных шаблона визуализации с настраиваемым дизайном, автоматическим извлечением цветов из обложки, Ambient Light эффектом и плавными анимациями. Все шаблоны оптимизированы для различных сценариев использования.

**Графический интерфейс управления:**

Предоставляется современный desktop-интерфейс для управления конфигурацией системы, запуска/остановки сервера, настройки параметров визуализации и мониторинга статуса работы всех компонентов.

## 4. Требования к программе

### 4.1 Требования к функциональным характеристикам

Данный раздел определяет функциональные требования к программе NowPlay, описывая основные возможности системы и требования к их реализации. Функциональные характеристики охватывают все аспекты работы программы — от мониторинга медиаплееров до визуализации информации и управления конфигурацией. Каждое требование сформулировано с использованием модального глагола "должна", что указывает на обязательность его выполнения.

#### 4.1.1 Мониторинг медиаплееров

Мониторинг медиаплееров является фундаментальной функцией системы, обеспечивающей автоматическое обнаружение и отслеживание воспроизведения музыкального контента на компьютере пользователя. Данный компонент работает в фоновом режиме, непрерывно опрашивая системный API для получения информации о текущей медиа-сессии.

Система должна обеспечивать автоматический мониторинг медиаплееров через Windows Media Control API с частотой опроса 1 секунда. Компонент должен автоматически определять активную медиа-сессию, извлекать метаданные трека и инициировать загрузку обложки при смене трека.

Поддерживаются медиаплееры: Spotify, Apple Music, YouTube Music, VLC, Windows Media Player, Groove Music, AIMP, foobar2000, MusicBee и веб-браузеры (Chrome, Firefox, Edge, Opera).

#### 4.1.2 Получение метаданных трека

Получение метаданных трека является критически важной функцией, обеспечивающей извлечение полной информации о воспроизводимом контенте. Метаданные используются для отображения информации в веб-виджетах и должны быть получены с минимальной задержкой для обеспечения актуальности отображаемых данных.

Система должна извлекать метаданные: исполнитель, название, альбом, длительность, текущая позиция, статус воспроизведения. Данные получаются из Windows Media Control API, дополнительно может использовать Last.fm, iTunes, Yandex Music, VK Music.

Метаданные должны быть в UTF-8 с нормализацией данных. Треки без названия отображаются как "Unknown Artist" / "Unknown Title".

#### 4.1.3 Получение обложек альбомов

Получение обложек альбомов является ключевой функцией визуализации, обеспечивающей привлекательное графическое представление информации о треке. Система использует интеллектуальную систему приоритизации источников и fallback-механизмы для обеспечения максимальной доступности изображений даже при недоступности отдельных API.

Система должна загружать обложки с приоритизацией источников: Windows Media Thumbnail API, Last.fm, iTunes, Yandex Music, VK Music. При недоступности источника автоматически переключается на следующий. Если все недоступны — используется дефолтная обложка.

Требования: максимальное время загрузки 3 секунды, форматы PNG/JPEG/WebP, размер 600x600 пикселей (минимум 300x300), максимум 5 МБ.

#### 4.1.4 Веб-сервер и API

Веб-сервер является центральным компонентом системы, обеспечивающим взаимодействие между всеми частями приложения и предоставляющим API для внешних клиентов. Асинхронная архитектура сервера позволяет эффективно обрабатывать множественные одновременные подключения с минимальной задержкой.

Встроенный асинхронный веб-сервер (aiohttp) работает на localhost:80. Предоставляет endpoints: POST /update_from_cs (обновления от C# компонента), GET /cover (получение обложки), GET /ws (WebSocket соединение), POST /update_config (обновление конфигурации), GET /sources (список источников), GET /{template}.html (шаблоны визуализации).

WebSocket обеспечивает real-time коммуникацию с троттлингом обновлений (минимум 100 мс между сообщениями). Время отклика API менее 10 мс, задержка WebSocket менее 100 мс.

#### 4.1.5 Визуализация треков

Визуализация является ключевым элементом пользовательского опыта, определяющим, как информация о треке будет представлена зрителям трансляции. Система предоставляет несколько профессиональных шаблонов, каждый из которых оптимизирован для различных сценариев использования и стилей оформления стримов.

Четыре шаблона: вертикальный (300x400), альтернативный (350x350), минималистичный (250x80), горизонтальный (600x120). Все поддерживают автоматическое извлечение цветов из обложки, настройку цветовой схемы, Ambient Light эффект, плавные анимации, прозрачный фон для OBS.

#### 4.1.6 Настройка внешнего вида

Гибкая настройка внешнего вида позволяет пользователям адаптировать визуализацию под стиль своего стрима, создавая уникальное оформление. Система предоставляет полный контроль над всеми визуальными параметрами через интуитивный графический интерфейс с возможностью предпросмотра изменений в реальном времени.

Настройка через GUI: цвета фона, акцентов, текста, прогресс-бара, визуализатора (RGB/RGBA/HEX), включение/отключение эффектов (волна, ambient light, автоцвета), позиционирование элементов. Изменения применяются в реальном времени через WebSocket.

#### 4.1.7 Графический интерфейс пользователя

Графический интерфейс является центром управления всей системой, предоставляя пользователю удобный доступ ко всем функциям программы. Интерфейс спроектирован с учетом принципов современного UX-дизайна, обеспечивая интуитивную навигацию и минимальное количество действий для выполнения типичных задач.

Desktop-приложение (CustomTkinter) с тремя страницами: Start (управление сервером, статус, копирование ссылки), Settings (настройка визуализации), Info (версия, документация, лицензия). Боковая панель навигации, визуальные индикаторы статуса.

#### 4.1.8 Интеграция C и Python компонентов

Интеграция разнородных компонентов является критически важным аспектом архитектуры системы, обеспечивающим бесшовное взаимодействие между C# модулем мониторинга и Python веб-сервером. Надежная синхронизация компонентов гарантирует своевременную доставку обновлений о текущем треке всем подключенным клиентам.

C# компонент (MediaMonitor) взаимодействует с Python сервером через HTTP POST запросы в формате JSON. При обнаружении изменений отправляет данные на /update_from_cs. Python сервер рассылает обновления WebSocket клиентам. Автоматическое переподключение при разрыве связи.

#### 4.1.9 Управление конфигурацией

Система управления конфигурацией обеспечивает сохранение пользовательских настроек между сессиями и их автоматическое применение при запуске приложения. Централизованное хранение конфигурации в формате JSON позволяет легко редактировать параметры как через графический интерфейс, так и вручную при необходимости.

Конфигурация хранится в config.json с параметрами визуализации, функциональности, позиционирования. Автоматическая загрузка при запуске, валидация значений, сохранение изменений через GUI.

### 4.2 Требования к надёжности

Надёжность системы определяет её способность стабильно функционировать в различных условиях эксплуатации, корректно обрабатывать ошибочные ситуации и автоматически восстанавливаться после сбоев. Требования к надёжности критически важны для стриминговых приложений, где любой сбой может негативно повлиять на качество трансляции.

#### 4.2.1 Обработка ошибок подключения к медиаплеерам

Устойчивость к отсутствию или некорректной работе медиаплееров является базовым требованием надёжности, обеспечивающим стабильную работу системы независимо от состояния внешних приложений.

Корректная обработка отсутствия медиаплееров без сбоев. При отсутствии медиа-сессии отправляется статус "inactive". Автоматическое восстановление при потере соединения.

#### 4.2.2 Стабильность работы веб-сервера

Стабильность веб-сервера критична для обеспечения непрерывной работы системы во время длительных стриминговых сессий, которые могут продолжаться многие часы без перерыва.

Непрерывная работа минимум 24 часа без перезапуска. Корректная обработка длительных сессий (48+ часов) без деградации производительности. Автоматическая очистка неактивных WebSocket соединений.

#### 4.2.3 Надёжность получения обложек

Надёжное получение обложек обеспечивается через систему резервных источников, гарантируя отображение изображений даже при недоступности отдельных API сервисов.

Fallback-стратегия при недоступности источников. Автоматическое переключение на следующий источник. Таймаут запросов 5 секунд. Кэширование обложек локально.

#### 4.2.4 Синхронизация C и Python компонентов

Надёжная синхронизация между разнородными компонентами системы обеспечивает бесперебойную передачу данных и автоматическое восстановление соединения при сбоях.

Надежная синхронизация с автоматическим переподключением. Python сервер должен запускать C# компонент при старте. Мониторинг состояния компонентов, уведомления о проблемах.

### 4.3 Требования к производительности

#### 4.3.1 Время реакции на смену трека

Обнаружение и обновление информации не более 2 секунд с момента переключения трека.

#### 4.3.2 Загрузка обложек

Загрузка обложек не более 3 секунд при скорости интернета минимум 1 Мбит/с. Асинхронная загрузка параллельно с обновлением текста.

#### 4.3.3 Нагрузка на CPU

Менее 2% при переключении треков, менее 0.5% в режиме ожидания. Стабильная нагрузка при длительной работе (24+ часа).

#### 4.3.4 Использование памяти

Python компонент: менее 150 МБ, C# компонент: менее 50 МБ. Общее использование менее 200 МБ. Отсутствие утечек памяти.

#### 4.3.5 Троттлинг обновлений

Минимальный интервал между WebSocket сообщениями 100 мс для предотвращения перегрузки клиентов.

#### 4.7.1 Порядок установки и запуска

Установка из готового установщика (NowPlay-Setup.exe) с автоматической установкой зависимостей (.NET 6.0 Runtime) или запуск из исходного кода (Python 3.12+, .NET 6.0 SDK, клонирование репозитория, установка зависимостей).

#### 4.7.2 Режимы работы

Первый запуск: запуск приложения, настройка параметров (опционально), нажатие START. Интеграция с OBS: добавление Browser Source с URL из приложения. Ежедневное использование: запуск приложения, START, воспроизведение музыки.

#### 4.7.3 Автоматический запуск

Опция автозапуска при загрузке ОС (добавление ярлыка в автозагрузку Windows). Автоматический запуск веб-сервера при старте приложения (настраивается).

#### 4.7.4 Обслуживание

Автоматическая ротация логов, очистка кэша, удаление временных файлов. Ручная очистка кэша, просмотр логов, сброс настроек (опционально). Проверка обновлений при запуске (опционально).

### 4.8 Требования к защите информации

#### 4.8.1 Сетевая безопасность

Веб-сервер работает только на localhost (127.0.0.1). Не принимает подключения из внешней сети. Порт 80 доступен только локально.

#### 4.8.2 Конфиденциальность данных

Все данные хранятся локально. Не собирается телеметрия. Не отправляется информация о треках на внешние серверы. Логи содержат только техническую информацию.

#### 4.8.3 Безопасность API

Валидация всех входных данных. Защита от инъекций (SQL, XSS, path traversal). Ограничение размера входных данных. Автоматическое закрытие неактивных WebSocket соединений.

Проверка обработки отсутствия медиаплееров, автовосстановления, fallback обложек, отсутствия утечек памяти, обработки некорректных данных.

Проверка работы с медиаплеерами (Spotify, VLC, браузеры), OBS Studio 28.0+, Windows 10/11, различными браузерами.

Проверка интуитивности интерфейса, понятности сообщений, скорости выполнения задач, качества документации.

#### 8.2.1 Автоматизированное тестирование

Unit-тесты для модулей, integration-тесты для взаимодействия, API-тесты для endpoints, автоматическое выполнение при изменениях.

#### 8.2.2 Ручное тестирование

Тестирование GUI на различных разрешениях, проверка визуализации в OBS, тестирование с медиаплеерами, проверка edge cases.

Длительная работа (48+ часов), частая смена треков (1000+ смен), множественные WebSocket подключения, измерение CPU и памяти.

#### 8.3.1 Функциональные критерии

Все функции из раздела 4.1 реализованы и работают. Отсутствуют критические ошибки. Все основные сценарии выполняются успешно.
