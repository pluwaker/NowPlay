# ТЕХНИЧЕСКОЕ ЗАДАНИЕ

## Проект: "Разработка кроссплатформенной системы управления и визуализации мультимедийного контента для стриминговых сервисов"

**Наименование программы:** NowPlay

**Версия документа:** 1.0

**Дата:** Декабрь 2024

---

## РАЗДЕЛ 1. ВВЕДЕНИЕ

### 1.1. Наименование и область применения

**Полное наименование программы:**  
NowPlay - система управления и визуализации мультимедийного контента для стриминговых сервисов

**Целевая аудитория:**
- Стримеры на платформах Twitch и YouTube Gaming
- Контент-криейторы, создающие видеоконтент
- Пользователи OBS Studio и Streamlabs OBS
- Музыкальные блогеры и подкастеры
- Профессиональные и начинающие стримеры

**Сфера использования:**
- Прямые трансляции (стриминг) на платформах Twitch, YouTube Gaming, Facebook Gaming
- Запись видеоконтента с отображением информации о воспроизводимой музыке
- Создание музыкальных шоу и подкастов
- Интеграция музыкального контента в игровые стримы
- Профессиональное оформление трансляций и видеозаписей

**Целевая операционная система:**
- Основная платформа: Windows 10 (64-bit) и Windows 11
- Минимальная версия: Windows 10 версии 1903 (May 2019 Update) и выше
- Возможность расширения: архитектура системы предусматривает будущую поддержку Linux (через MPRIS D-Bus) и macOS (через MediaPlayer framework)

**Область применения:**  
Программа предназначена для использования в домашних и профессиональных условиях при создании стримингового и видеоконтента. Система обеспечивает автоматическое отображение информации о текущем воспроизводимом музыкальном треке непосредственно в трансляции или записи, что повышает качество контента и улучшает взаимодействие с аудиторией.

### 1.2. Краткая характеристика области применения

**Основное назначение программы:**

NowPlay представляет собой комплексное решение для автоматического отображения информации о текущем воспроизводимом мультимедийном контенте в стриминговых приложениях. Программа осуществляет мониторинг активных медиаплееров на компьютере пользователя, получает метаданные о воспроизводимых треках, загружает обложки альбомов из различных источников и предоставляет настраиваемые веб-виджеты для визуализации этой информации в OBS Studio или других стриминговых приложениях.

**Ключевые возможности системы:**

1. **Автоматический мониторинг медиаплееров**
   - Отслеживание воспроизведения музыки из любого медиаплеера, поддерживающего Windows Media Control API
   - Поддержка популярных приложений: Spotify, VLC Media Player, Windows Media Player, Groove Music, веб-браузеры (Chrome, Firefox, Edge)
   - Частота опроса: 1 секунда для обеспечения быстрой реакции на смену треков
   - Автоматическое определение смены трека без участия пользователя

2. **Получение метаданных и обложек**
   - Извлечение полной информации о треке: исполнитель, название, альбом, длительность, текущая позиция воспроизведения
   - Автоматическая загрузка обложек альбомов из множественных источников с приоритизацией
   - Поддержка API: Last.fm, iTunes Search API, Yandex Music, VK Music
   - Интеллектуальная система fallback при недоступности источника
   - Кэширование обложек для оптимизации производительности

3. **Настраиваемая визуализация**
   - 4 профессиональных шаблона визуализации: вертикальный, альтернативный, минималистичный, горизонтальный
   - Полная настройка цветовой схемы: фон, акцентные цвета, текст, прогресс-бар, визуализатор
   - Автоматическое извлечение доминирующих цветов из обложки альбома для создания гармоничной палитры
   - Ambient Light эффект - динамическая подсветка обложки
   - Настройка позиционирования элементов на экране
   - Плавные анимации и переходы между треками

4. **Веб-сервер и API**
   - Встроенный асинхронный веб-сервер на базе aiohttp
   - RESTful API для получения информации о текущем треке
   - WebSocket соединение для real-time обновлений без задержек
   - Endpoints: получение обложки, обновление конфигурации, получение списка источников
   - Работа на localhost (127.0.0.1) для обеспечения безопасности

5. **Графический интерфейс пользователя**
   - Современный desktop-интерфейс на базе CustomTkinter
   - Три основные страницы: Start (управление сервером), Settings (настройка параметров), Info (информация о приложении)
   - Интуитивная боковая панель навигации
   - Визуальные индикаторы статуса работы системы
   - Простое копирование ссылки для добавления в OBS Studio одним кликом

6. **Оптимизированная производительность**
   - Минимальная нагрузка на CPU: менее 2% при переключении треков, менее 0.5% в режиме ожидания
   - Использование памяти: менее 150 МБ для Python компонента, менее 50 МБ для C# компонента
   - Оптимизированный алгоритм извлечения цветов с использованием Canvas API
   - Троттлинг обновлений для предотвращения перегрузки клиентов
   - Стабильная работа 24+ часа без перезапуска

7. **Интеграция с OBS Studio**
   - Бесшовная интеграция через Browser Source
   - Поддержка OBS Studio 28.0+ и Streamlabs OBS
   - Прозрачный фон для наложения на любой контент
   - Адаптивный дизайн виджетов
   - Возможность использования нескольких виджетов одновременно

**Технологическая платформа:**

Система построена на основе гибридной архитектуры, объединяющей преимущества различных технологий:

- **Backend (Python 3.12+):**
  - Веб-сервер: aiohttp 3.8+ (асинхронный HTTP сервер и WebSocket)
  - GUI: CustomTkinter 5.0+ (современный графический интерфейс)
  - Управление конфигурацией: JSON-based config manager
  - Асинхронное программирование для высокой производительности

- **System Monitor (C# .NET 6.0+):**
  - Windows Media Control API для мониторинга медиаплееров
  - Высокая производительность и низкая задержка
  - Нативная интеграция с Windows
  - HTTP клиент для взаимодействия с Python сервером

- **Frontend (HTML5/CSS3/JavaScript):**
  - Canvas API для обработки изображений и извлечения цветов
  - WebSocket API для real-time обновлений
  - CSS3 анимации и transitions
  - Адаптивный дизайн

**Режимы работы:**

1. **Desktop-приложение с GUI:**
   - Запуск через главное окно приложения
   - Управление сервером (старт/стоп)
   - Настройка всех параметров через графический интерфейс
   - Мониторинг статуса системы в реальном времени

2. **Веб-сервер с API:**
   - Работает на localhost:80
   - Предоставляет RESTful API для внешних приложений
   - WebSocket сервер для push-уведомлений
   - Может работать в фоновом режиме

3. **Веб-виджеты для браузера:**
   - Отображаются в OBS Studio через Browser Source
   - Могут использоваться в любом веб-браузере
   - Автоматическое обновление при смене трека
   - Настраиваемый внешний вид через конфигурацию

4. **Гибридный режим (для разработки):**
   - Одновременная работа Python и C# мониторинга
   - Используется для отладки и тестирования
   - Позволяет сравнивать производительность компонентов

**Архитектурные особенности:**

Система построена по трёхуровневой архитектуре:
- **Уровень 1:** Desktop Application (GUI, управление конфигурацией)
- **Уровень 2:** Web Server (API, WebSocket, бизнес-логика)
- **Уровень 3:** Frontend Widgets (визуализация, пользовательский интерфейс)

Такая архитектура обеспечивает:
- Разделение ответственности между компонентами
- Возможность независимого развития каждого уровня
- Кроссплатформенность (веб-технологии работают везде)
- Масштабируемость и расширяемость системы

Разработка является инициативным проектом, направленным на создание бесплатного альтернативного решения существующим коммерческим продуктам в области отображения информации о воспроизводимой музыке для стримеров и контент-криейторов.

### 2.2. Цель разработки

Целью разработки является создание кроссплатформенной системы управления и визуализации мультимедийного контента для стриминговых сервисов с автоматическим отображением информации о текущем воспроизводимом треке, обеспечивающей высокую производительность, гибкую настройку визуализации и бесшовную интеграцию с популярными стриминговыми приложениями.

Анализ существующих решений в области отображения информации о воспроизводимой музыке для стримеров выявил ряд существенных проблем, препятствующих эффективному использованию таких систем. Коммерческие решения, такие как Streamlabs Ultra ($19/месяц или $228/год), XSplit Broadcaster Premium ($25/месяц, $300/год или $199 за пожизненную лицензию) и Pretzel Rocks Pro ($15/месяц или $180/год), требуют значительных финансовых затрат, что создает существенный барьер для начинающих стримеров и студентов. При этом бесплатные альтернативы обладают крайне ограниченной функциональностью: например, Snip поддерживает только Spotify и не предоставляет визуализацию обложек, а OBS Now Playing имеет базовый функционал без возможности настройки внешнего вида.

Серьезной проблемой существующих решений является высокая нагрузка на системные ресурсы. Многие программы используют неоптимизированные алгоритмы обработки изображений, что приводит к нагрузке на CPU в диапазоне 15-35% при обработке обложек и избыточному использованию оперативной памяти (более 300 МБ). Это негативно влияет на производительность стриминга и игр, что критично для пользователей с ограниченными аппаратными ресурсами. Кроме того, большинство решений работают только на Windows, вынуждая пользователей Linux и macOS искать сложные обходные пути или отказываться от использования подобных инструментов.

Дополнительную сложность создает ограниченная поддержка источников метаданных. Многие решения зависят от единственного API (обычно Last.fm или Spotify) и не имеют fallback-механизмов при недоступности источника, что приводит к проблемам с получением обложек для локальных файлов и отсутствию поддержки региональных сервисов, таких как Yandex Music и VK Music. Сложность настройки и использования, отсутствие интуитивного графического интерфейса и недостаточная документация также снижают доступность существующих решений для широкой аудитории.

Актуальность разработки системы NowPlay подтверждается динамичным ростом индустрии стриминга и возрастающими требованиями к качеству контента. По данным Twitch Tracker (2024), на платформе Twitch зарегистрировано более 9.5 миллионов активных стримеров, а YouTube Gaming насчитывает более 40 миллионов игровых каналов. Среднее количество одновременных зрителей на Twitch превышает 2.5 миллиона человек, а рынок стримингового оборудования и программного обеспечения оценивается в $4.3 миллиарда (2024). Эти цифры демонстрируют масштаб индустрии и потенциальную аудиторию разрабатываемого решения.

Музыкальный контент играет ключевую роль в стриминге: согласно исследованию StreamElements (2024), 78% стримеров используют фоновую музыку во время трансляций, а 65% зрителей отмечают важность качественного аудиосопровождения. Музыкальные стримы и подкасты составляют 12% от общего контента на Twitch, при этом интеграция музыки повышает вовлеченность аудитории на 23% (исследование StreamLabs, 2023). Спрос на инструменты визуализации подтверждается тем, что 89% профессиональных стримеров используют кастомные оверлеи и виджеты, а поиск "now playing OBS" в Google показывает 2.4 миллиона результатов. Тема "Music Display Widget" на форуме OBS имеет более 500,000 просмотров, а запросы на бесплатные альтернативы платным решениям растут на 35% ежегодно.

С технологической точки зрения проект соответствует современным трендам разработки программного обеспечения. Наблюдается переход на асинхронное программирование для повышения производительности, активное использование веб-технологий для обеспечения кроссплатформенности, акцент на оптимизацию ресурсов для одновременного стриминга и игр, а также растущая популярность open-source решений в стриминг-сообществе. Образовательная значимость проекта заключается в демонстрации интеграции различных технологий (Python, C#, JavaScript), практическом применении системных API (Windows Media Control), реализации асинхронного веб-сервера и WebSocket коммуникации, а также оптимизации производительности и алгоритмов обработки изображений.

Анализ потребностей целевой аудитории показывает, что стримеры и контент-криейторы нуждаются в экономически доступном решении без ограничений функциональности, подписок и скрытых платежей, желательно с открытым исходным кодом для возможности модификации. Критически важна простота использования: интуитивный графический интерфейс, быстрая интеграция с OBS Studio (1-2 клика), автоматическая настройка без необходимости редактирования конфигурационных файлов и подробная документация. При этом пользователи требуют гибкости настройки, включая множество шаблонов визуализации, полную настройку цветовой схемы, автоматическое извлечение цветов из обложки и настройку позиционирования элементов.

Высокая производительность является обязательным требованием: минимальная нагрузка на CPU (менее 2%), низкое потребление памяти (менее 200 МБ), отсутствие влияния на FPS в играх и стабильная работа во время длительных стримов продолжительностью 24 часа и более. Необходима широкая совместимость с популярными медиаплеерами (Spotify, VLC, браузеры), работа с OBS Studio и Streamlabs OBS, получение метаданных из множественных источников и перспектива кроссплатформенности (Linux, macOS). Надежность и стабильность системы должны обеспечиваться автоматическим восстановлением при ошибках, fallback-механизмами для получения обложек, корректной обработкой отсутствия интернет-соединения и отсутствием критических сбоев во время трансляции.

В результате выполнения разработки ожидается создание полнофункционального программного обеспечения, включающего desktop-приложение с графическим интерфейсом для Windows 10/11, веб-сервер с RESTful API и WebSocket поддержкой, четыре настраиваемых шаблона визуализации для OBS Studio, C# компонент для мониторинга медиаплееров через Windows Media Control API и систему получения метаданных и обложек из множественных источников. Для удобства распространения будет подготовлен инсталлятор для Windows (NowPlay-Setup.exe) и портативная версия, не требующая установки, со всеми необходимыми зависимостями и автоматической настройкой при первом запуске.

Неотъемлемой частью проекта является комплексная документация, включающая техническое задание по ГОСТ 19.201-78, руководство пользователя с иллюстрациями, техническую документацию для разработчиков, README с инструкциями по установке и использованию, а также API документацию для интеграции с внешними приложениями. ## РАЗДЕЛ 3. НАЗНАЧЕНИЕ РАЗРАБОТКИ

### 3.1. Функциональное и эксплуатационное назначение

**Функциональное назначение:**

Основной функцией программы NowPlay является автоматическое отображение информации о текущем воспроизводимом мультимедийном контенте в стриминговых приложениях и видеозаписях. Система осуществляет непрерывный мониторинг активных медиаплееров на компьютере пользователя, извлекает метаданные о воспроизводимых треках и автоматически загружает обложки альбомов из множественных источников, предоставляя визуальное представление этой информации через настраиваемые веб-виджеты.

Программа решает задачу информирования зрителей о музыкальном контенте, звучащем во время трансляции или в записанном видео, без необходимости ручного ввода данных стримером. Это позволяет зрителям узнавать названия понравившихся треков, повышает профессионализм оформления контента и улучшает взаимодействие между стримером и аудиторией. Система работает полностью автоматически, не требуя вмешательства пользователя после первоначальной настройки, что позволяет стримеру сосредоточиться на создании контента, а не на технических аспектах отображения информации о музыке.

Функциональные возможности системы охватывают полный цикл обработки мультимедийной информации. Система автоматически определяет текущий воспроизводимый трек из любого медиаплеера, поддерживающего Windows Media Control API, получает полные метаданные трека включая исполнителя, название, альбом, длительность и текущую позицию воспроизведения. Обложки альбомов загружаются автоматически из множественных источников с интеллектуальной приоритизацией, после чего система извлекает доминирующие цвета из обложки для создания гармоничной цветовой палитры виджета. Визуализация информации осуществляется через настраиваемые веб-виджеты с поддержкой анимаций и эффектов, при этом обновление отображаемой информации происходит в реальном времени при смене трека или изменении позиции воспроизведения. Пользователь имеет возможность настраивать внешний вид виджетов, включая цветовую схему, позиционирование, выбор шаблонов и визуальные эффекты, а также управлять конфигурацией через графический интерфейс с автоматическим сохранением настроек.

**Эксплуатационное назначение:**

Программа NowPlay предназначена для эксплуатации в трех основных режимах использования, каждый из которых ориентирован на определенные сценарии применения.

Первым и наиболее распространенным является режим интеграции с OBS Studio через Browser Source. Этот режим предназначен для стримеров и контент-криейторов, работающих с OBS Studio или Streamlabs OBS. Веб-виджет NowPlay добавляется в сцену OBS как источник типа "Browser Source", что позволяет отображать информацию о текущем треке непосредственно в трансляции или записи видео. Процесс интеграции максимально упрощен: пользователь запускает desktop-приложение NowPlay и нажимает кнопку START для запуска веб-сервера, после чего в приложении отображается готовая ссылка на выбранный шаблон визуализации. Эту ссылку можно скопировать одним кликом и вставить при создании нового источника типа "Browser Source" в OBS Studio, после чего виджет автоматически появляется в сцене и начинает отображать информацию о текущем треке.

Данный режим обеспечивает бесшовную интеграцию с существующим workflow стримера, при этом виджет отображается только в трансляции или записи, не занимая место на экране пользователя. Прозрачный фон виджета позволяет накладывать его на любой контент с поддержкой всех визуальных эффектов и анимаций. Система поддерживает возможность использования нескольких виджетов одновременно в разных сценах OBS с автоматическим обновлением информации без перезагрузки источника. Режим совместим с OBS Studio версии 28.0 и выше, Streamlabs OBS всех актуальных версий, а также любыми другими стриминговыми приложениями, поддерживающими Browser Source или веб-контент.

Второй режим представляет собой standalone веб-интерфейс, в котором веб-виджет NowPlay открывается непосредственно в веб-браузере пользователя, независимо от стримингового программного обеспечения. Этот автономный режим предназначен для тестирования и предварительного просмотра виджетов перед добавлением в OBS, использования на втором мониторе для личного контроля воспроизводимой музыки, демонстрации функциональности системы, а также разработки и отладки новых шаблонов визуализации. Пользователь просто открывает в браузере адрес соответствующего шаблона и получает полнофункциональный виджет с автоматическим обновлением информации о треках. Режим поддерживает все современные браузеры, включая Google Chrome, Mozilla Firefox, Microsoft Edge и Opera.

Автономный режим не требует установки OBS Studio и позволяет использовать виджет на любом устройстве в локальной сети. Он удобен для тестирования настроек и шаблонов, может использоваться для создания скриншотов и демонстрационных материалов, при этом поддерживая все функции, доступные в режиме интеграции с OBS.

Третий режим представлен графическим desktop-приложением, которое является центром управления всей системой и предоставляет интуитивный интерфейс для конфигурации. Приложение организовано в виде трех основных страниц. Страница Start обеспечивает управление сервером с возможностью запуска и остановки веб-сервера одной кнопкой, отображением статуса работы системы и индикацией текущего воспроизводимого трека в реальном времени, а также предоставляет функцию копирования ссылки на виджет для добавления в OBS и выбор активного шаблона визуализации из выпадающего списка. Страница Settings предназначена для настройки параметров визуализации, включая выбор одного из четырех шаблонов, настройку цветовой схемы всех элементов интерфейса, управление автоматическим извлечением цветов из обложки, позиционирование элементов на экране и включение визуальных эффектов. Страница Info отображает версию программы и компонентов, предоставляет ссылки на документацию и репозиторий, информацию о лицензии и список поддерживаемых медиаплееров.

Desktop-приложение работает в фоновом режиме и может быть свернуто в системный трей, автоматически запуская необходимые компоненты и обеспечивая их корректное взаимодействие. Все настройки сохраняются в конфигурационный файл, который автоматически загружается при следующем запуске системы.

Помимо основных режимов, система поддерживает режим разработки для продвинутых пользователей, позволяющий запускать приложение из исходного кода Python для модификации функциональности, получать доступ к API endpoints для интеграции с внешними приложениями и создавать собственные шаблоны визуализации. Гибридный режим используется разработчиками для отладки и предусматривает одновременную работу Python и C# компонентов мониторинга медиаплееров, что позволяет сравнивать производительность различных компонентов и тестировать fallback-механизмы.

Все режимы эксплуатации могут работать одновременно, что обеспечивает максимальную гибкость использования системы. Например, пользователь может управлять настройками через desktop-приложение, одновременно используя виджет в OBS Studio для трансляции и открыв standalone версию в браузере на втором мониторе для личного контроля.

### 3.2. Краткое описание предоставляемых сервисов

Система NowPlay предоставляет комплекс взаимосвязанных сервисов, обеспечивающих полный цикл обработки информации о мультимедийном контенте - от мониторинга медиаплееров до визуализации данных в стриминговых приложениях. Архитектура системы построена по модульному принципу, где каждый сервис выполняет специализированную функцию и взаимодействует с другими компонентами через четко определенные интерфейсы. Основными компонентами системы являются сервис мониторинга медиаплееров для автоматического отслеживания воспроизведения музыки через системные API, сервис получения метаданных треков для извлечения информации из различных источников, сервис загрузки обложек альбомов с приоритизацией источников, веб-сервер с API и WebSocket для предоставления данных клиентским приложениям в реальном времени, сервис визуализации треков для отображения информации через настраиваемые веб-виджеты, а также сервис настройки и конфигурации для управления параметрами системы через графический интерфейс.

Сервис мониторинга медиаплееров является фундаментальным компонентом системы, обеспечивающим автоматическое обнаружение и отслеживание воспроизведения музыкального контента на компьютере пользователя. Сервис реализован в виде C# компонента, использующего Windows Media Control API для получения информации о текущей медиа-сессии. Принцип работы основан на периодическом опросе системного API с частотой один раз в секунду, при котором проверяется наличие активной медиа-сессии, извлекаются метаданные текущего трека включая исполнителя, название и альбом, определяется статус воспроизведения и получается информация о позиции воспроизведения и общей длительности трека. При обнаружении смены трека автоматически инициируется загрузка обложки.

Сервис автоматически работает со всеми приложениями, поддерживающими Windows Media Control API, включая музыкальные стриминговые сервисы такие как Spotify, Apple Music и YouTube Music, медиаплееры VLC Media Player, Windows Media Player, Groove Music, AIMP, foobar2000 и MusicBee, а также веб-браузеры Google Chrome, Mozilla Firefox, Microsoft Edge и Opera при воспроизведении музыки на веб-сайтах. Технические характеристики сервиса обеспечивают время реакции на смену трека менее двух секунд при нагрузке на CPU менее 0.3% в режиме ожидания и менее 1.5% при смене трека, с использованием памяти менее 50 МБ и автоматическим восстановлением при потере соединения с медиаплеером.

Сервис корректно обрабатывает особые случаи, включая отсутствие активной медиа-сессии с отправкой статуса "inactive" на Python сервер, наличие нескольких активных медиаплееров с использованием последнего активированного, треки без метаданных и Unicode символы в названиях треков. Интеграция с системой осуществляется через работу сервиса как отдельного процесса, взаимодействующего с Python веб-сервером через HTTP POST запросы, при этом при обнаружении изменений в воспроизведении формируется JSON объект с актуальными данными, который отправляется на сервер для последующего распространения обновлений всем подключенным клиентам через WebSocket.

Сервис получения метаданных треков отвечает за извлечение полной информации о воспроизводимом треке, включая данные, которые могут отсутствовать в системном API медиаплеера. Этот сервис работает в связке с сервисом мониторинга и обогащает базовую информацию дополнительными данными из внешних источников. Извлекаемые метаданные включают основную информацию об исполнителе, названии трека и альбоме, временные параметры такие как текущая позиция воспроизведения и общая длительность трека в секундах, статус воспроизведения, техническую информацию для кэширования обложек и статус системы, а также дополнительные данные о жанре, годе выпуска и номере трека в альбоме при наличии в источнике.

Система использует множественные источники метаданных, начиная с Windows Media Control API как первичного источника, предоставляющего базовую информацию непосредственно от медиаплеера, и дополняя её данными из Last.fm API, iTunes Search API, Yandex Music API и VK Music API. Обработка и нормализация данных включает удаление лишних пробелов и специальных символов из названий, приведение к единому формату кодировки UTF-8, обработку различных форматов представления исполнителей и нормализацию длительности трека с валидацией корректности полученных данных. Для оптимизации производительности и снижения количества запросов к внешним API сервис использует многоуровневое кэширование с кэшем в памяти для быстрого доступа к недавно воспроизведенным трекам, локальным хранилищем для долгосрочного кэширования и автоматической инвалидацией устаревших данных.

Сервис загрузки обложек альбомов обеспечивает автоматическое получение изображений обложек из различных источников с интеллектуальной системой приоритизации и fallback-механизмами, что критически важно для визуальной привлекательности виджетов и реализации функции автоматического извлечения цветов. Архитектура сервиса состоит из двух компонентов: C# CoverFetcher для быстрого получения обложки непосредственно из медиаплеера через Thumbnail API и Python cover_fetcher.py для загрузки обложек из внешних источников при недоступности локальной обложки.

Система использует иерархическую приоритизацию источников обложек, начиная с Windows Media Thumbnail API с наивысшим приоритетом для получения обложки непосредственно от медиаплеера с мгновенной доступностью без сетевых запросов, затем обращаясь к Last.fm API с обширной базой данных обложек и хорошим покрытием западной музыки, iTunes Search API с официальным каталогом Apple Music и высоким качеством изображений до 3000x3000 пикселей, Yandex Music API со специализацией на русскоязычной музыке и хорошим покрытием российских исполнителей, и наконец VK Music API как дополнительный источник для русскоязычного контента. Механизм fallback последовательно пытается получить обложку из каждого источника, переходя к следующему при неудаче, и в случае недоступности всех источников использует дефолтную обложку.

Технические характеристики сервиса обеспечивают максимальное время загрузки обложки три секунды с поддержкой форматов PNG, JPEG и WebP, оптимальным размером изображения 600x600 пикселей, кэшированием обложек в локальной папке и версионированием для корректного обновления в браузере. Оптимизация включает локальное сохранение обложек для предотвращения повторной загрузки одного и того же трека, использование HTTP заголовков для кэширования, параллельную загрузку обложки и получение метаданных для минимизации задержки, а также опциональную предзагрузку обложек для следующих треков в плейлисте.

Веб-сервер является центральным компонентом системы, обеспечивающим взаимодействие между всеми модулями и предоставляющим данные клиентским приложениям. Сервер реализован на базе асинхронного фреймворка aiohttp, что обеспечивает высокую производительность и возможность обработки множественных одновременных соединений. Архитектура включает асинхронный HTTP сервер, WebSocket сервер для real-time обновлений, статический файловый сервер для HTML/CSS/JavaScript виджетов и API endpoints для взаимодействия с компонентами системы.

HTTP API предоставляет несколько ключевых endpoints: POST /update_from_cs для получения обновлений от C# MediaMonitor с последующим обновлением глобального состояния и рассылкой через WebSocket, GET /cover для получения изображения обложки текущего трека с версионированием для обхода кэша браузера, GET /ws для установки WebSocket соединения с поддержкой различных типов сообщений включая начальное состояние, обновление данных и изменение конфигурации, POST /update_config для обновления конфигурации системы с сохранением в файл и уведомлением всех клиентов, GET /sources для получения списка доступных источников обложек, а также GET /{template}.html для статической раздачи HTML файлов виджетов.

Сервер поддерживает двунаправленную коммуникацию через WebSocket для обеспечения мгновенного обновления информации в виджетах без необходимости постоянного опроса сервера. Система использует троттлинг с минимальным интервалом между WebSocket обновлениями 100 миллисекунд для предотвращения перегрузки клиентов при частых изменениях позиции воспроизведения, автоматическую очистку неактивных соединений и graceful shutdown при остановке сервера. Технические характеристики обеспечивают работу на порту 80 с адресом localhost для безопасности, неограниченное количество одновременных WebSocket соединений в зависимости от системных ресурсов, время отклика API менее 10 миллисекунд и задержку WebSocket обновлений менее 100 миллисекунд.

Сервис визуализации треков предоставляет четыре профессиональных шаблона для отображения информации о текущем треке, каждый из которых оптимизирован для различных сценариев использования и эстетических предпочтений. Вертикальный шаблон представляет собой классический layout с обложкой сверху и информацией снизу, оптимальный для размещения в углах экрана с размерами 300x400 пикселей и включающий ambient light эффект вокруг обложки с плавными анимациями. Альтернативный шаблон является модернизированной версией с акцентом на типографику, оптимальной для минималистичных стримов с размерами 350x350 пикселей, градиентным фоном и адаптивным размером текста. Минималистичный шаблон предлагает ультра-компактный дизайн для ненавязчивого отображения в игровых стримах с размерами 250x80 пикселей, полупрозрачным фоном и быстрыми анимациями. Горизонтальный шаблон представляет широкий layout для размещения внизу экрана с размерами 600x120 пикселей, кинематографическим форматом и динамическим фоном.

Все шаблоны обладают общими возможностями, включая автоматическое извлечение доминирующих цветов из обложки для создания гармоничной палитры, настройку всех цветов через конфигурацию, плавные CSS transitions для всех изменений, адаптивный дизайн с поддержкой различных разрешений, прозрачный фон для наложения на любой контент, поддержку Unicode символов, автоматическое обрезание длинных названий и анимацию прогресс-бара в реальном времени. Визуальные эффекты включают динамическую подсветку Ambient Light вокруг обложки, анимированный волновой визуализатор, плавные переходы при смене трека, эффекты размытия для фоновых элементов и свечение акцентных элементов. Технические характеристики обеспечиваются использованием HTML5, CSS3 и JavaScript с Canvas API для обработки изображений и извлечения цветов, WebSocket для real-time обновлений, оптимизированным алгоритмом извлечения цветов с нагрузкой CPU менее 2%, кэшированием цветовых палитр и дебаунсингом обновлений для предотвращения мерцания.

Сервис настройки и конфигурации обеспечивает удобное управление всеми параметрами системы через графический интерфейс и автоматическое сохранение настроек для последующего использования. Управляемые параметры включают визуальные настройки такие как выбор шаблона визуализации из четырех вариантов, настройку цветов фона, акцентных элементов, контейнеров, волны визуализатора, текста и прогресс-бара в форматах RGB, RGBA или HEX, функциональные настройки для включения или отключения волнового визуализатора, ambient light эффекта, автоматического извлечения цветов из обложки, выбора источника мониторинга и активного медиаплеера, а также настройки позиционирования с горизонтальным и вертикальным выравниванием и девятью предустановленными позициями для размещения в углах и центрах сторон экрана.

Все настройки сохраняются в файле config.json в корне проекта в формате JSON, содержащем все параметры визуализации, функциональности и позиционирования. Механизм обновления конфигурации работает следующим образом: пользователь изменяет настройки в графическом интерфейсе на странице Settings, при нажатии кнопки сохранения данные отправляются на сервер через POST запрос, сервер сохраняет изменения в файл конфигурации и рассылает обновление всем подключенным WebSocket клиентам, после чего виджеты автоматически применяют новые настройки без перезагрузки страницы. Система включает валидацию настроек с проверкой корректности цветовых значений, валидацией диапазонов числовых параметров, проверкой существования выбранного шаблона и автоматическим исправлением некорректных значений на значения по умолчанию. Дополнительно поддерживается работа с пресетами и профилями, включая возможность сохранения пользовательских пресетов настроек, быстрое переключение между профилями и экспорт или импорт конфигурации для обмена с другими пользователями.

Система NowPlay разработана для широкого круга пользователей, работающих с мультимедийным контентом. Основную целевую аудиторию составляют стримеры на платформах Twitch и YouTube Gaming, включая как профессиональных стримеров с постоянной аудиторией, так и начинающих создателей контента, музыкальных стримеров, DJ и игровых стримеров, использующих фоновую музыку. Система также ориентирована на контент-криейторов, включая видеоблогеров, создателей подкастов и аудиоконтента, музыкальных блогеров и обозревателей, а также создателей обучающего контента. Важной категорией пользователей являются все работающие с OBS Studio версии 28.0 и выше, Streamlabs OBS и другими стриминговыми приложениями с поддержкой Browser Source. Дополнительно система предназначена для энтузиастов и разработчиков, желающих расширить функциональность системы, дизайнеров, создающих собственные шаблоны визуализации, студентов, изучающих веб-технологии и системное программирование, а также open-source контрибьюторов.

Система предоставляет решение для всех уровней пользователей - от начинающих стримеров, которым нужен простой в использовании инструмент, до профессионалов, требующих гибкой настройки и высокой производительности. Модульная архитектура и открытый исходный код позволяют разработчикам адаптировать систему под специфические требования и создавать собственные расширения.

## РАЗДЕЛ 4. ТРЕБОВАНИЯ К ПРОГРАММЕ

### 4.1. Требования к функциональным характеристикам

Функциональные характеристики программы NowPlay определяют основные возможности системы и требования к их реализации. Данный раздел детально описывает все функциональные компоненты системы, их взаимодействие и технические параметры работы.

#### 4.1.1. Мониторинг медиаплееров

Система SHALL обеспечивать автоматический мониторинг активных медиаплееров на компьютере пользователя через Windows Media Control API (GlobalSystemMediaTransportControlsSessionManager). Мониторинг SHALL осуществляться с частотой опроса один раз в секунду для обеспечения быстрой реакции на изменения в воспроизведении.

Компонент мониторинга SHALL автоматически определять наличие активной медиа-сессии в системе и извлекать базовые метаданные текущего трека непосредственно от медиаплеера. При обнаружении смены трека (изменение исполнителя или названия) система SHALL немедленно инициировать процесс загрузки обложки и обновления информации.

Система SHALL поддерживать все медиаплееры, использующие Windows Media Control API, включая:
- Музыкальные стриминговые сервисы: Spotify, Apple Music, YouTube Music, Deezer, Tidal
- Медиаплееры: VLC Media Player, Windows Media Player, Groove Music, AIMP, foobar2000, MusicBee
- Веб-браузеры: Google Chrome, Mozilla Firefox, Microsoft Edge, Opera (при воспроизведении музыки на веб-сайтах)

При отсутствии активной медиа-сессии система SHALL отправлять статус "inactive" на веб-сервер для корректного отображения состояния в пользовательском интерфейсе. Компонент мониторинга SHALL работать как отдельный процесс (MediaMonitor.exe) и автоматически восстанавливать соединение с Python сервером при разрыве связи.

#### 4.1.2. Получение метаданных треков

Система SHALL извлекать полный набор метаданных о воспроизводимом треке, включая следующие обязательные поля:
- **Artist** (Исполнитель): строковое значение, содержащее имя исполнителя или группы
- **Title** (Название трека): строковое значение с названием композиции
- **Album** (Альбом): строковое значение с названием альбома (опционально)
- **Duration** (Длительность): числовое значение в секундах, представляющее общую длительность трека
- **Position** (Текущая позиция): числовое значение в секундах, представляющее текущую позицию воспроизведения
- **IsPlaying** (Статус воспроизведения): булево значение, указывающее, воспроизводится ли трек в данный момент (true) или находится на паузе (false)

Система SHALL получать метаданные из первичного источника - Windows Media Control API, который предоставляет информацию непосредственно от медиаплеера. Для обогащения данных система MAY использовать дополнительные источники, включая Last.fm API, iTunes Search API, Yandex Music API и VK Music API.

Все текстовые метаданные SHALL быть представлены в кодировке UTF-8 для корректной обработки Unicode символов, включая кириллицу, иероглифы и специальные символы. Система SHALL выполнять нормализацию данных, включая удаление лишних пробелов в начале и конце строк, приведение к единому формату представления и валидацию корректности полученных значений.

При получении метаданных система SHALL обрабатывать особые случаи:
- Треки без названия или исполнителя SHALL отображаться как "Unknown Artist" / "Unknown Title"
- Отсутствие информации о длительности SHALL обрабатываться корректно без ошибок
- Некорректные значения позиции воспроизведения SHALL быть отфильтрованы

#### 4.1.3. Получение обложек альбомов

Система SHALL автоматически загружать обложки альбомов для текущего воспроизводимого трека с использованием интеллектуальной системы приоритизации источников и fallback-механизмов для обеспечения максимальной доступности изображений.

Система SHALL использовать следующую иерархию источников обложек с указанным порядком приоритета:

1. **Windows Media Thumbnail API** (наивысший приоритет):
   - Получение обложки непосредственно от медиаплеера через системный API
   - Мгновенная доступность без сетевых запросов
   - Используется C# компонентом CoverFetcher

2. **Last.fm API**:
   - Обширная база данных обложек альбомов
   - Хорошее покрытие западной музыки
   - Поддержка различных размеров изображений

3. **iTunes Search API**:
   - Официальный каталог Apple Music
   - Высокое качество изображений (до 3000x3000 пикселей)
   - Надежность и стабильность сервиса

4. **Yandex Music API**:
   - Специализация на русскоязычной музыке
   - Хорошее покрытие российских исполнителей
   - Поддержка локального контента

5. **VK Music API**:
   - Дополнительный источник для русскоязычного контента
   - Альтернатива при недоступности других источников

Система SHALL реализовать механизм fallback, при котором в случае неудачи получения обложки из источника с более высоким приоритетом автоматически выполняется попытка загрузки из следующего источника в списке. Если все источники недоступны или не содержат обложку для данного трека, система SHALL использовать дефолтную обложку (songinfo/NoCover.png).

Технические требования к обложкам:
- Максимальное время загрузки: 3 секунды
- Поддерживаемые форматы: PNG, JPEG, WebP
- Оптимальный размер изображения: 600x600 пикселей
- Минимальный размер: 300x300 пикселей
- Максимальный размер файла: 5 МБ

Система SHALL сохранять загруженные обложки локально в папке songinfo/cover.png для предотвращения повторной загрузки при воспроизведении того же трека. Для обеспечения корректного обновления обложки в браузере система SHALL использовать версионирование через параметр запроса (cover_version), который инкрементируется при каждой смене трека.

Система SHALL выполнять параллельную загрузку обложки и получение метаданных для минимизации общей задержки обновления информации. При смене трека обложка SHALL загружаться асинхронно, не блокируя обновление текстовой информации о треке.

#### 4.1.4. Веб-сервер и API

Система SHALL включать встроенный асинхронный веб-сервер на базе фреймворка aiohttp, работающий на порту 80 по адресу localhost (127.0.0.1) для обеспечения безопасности и предотвращения внешнего доступа.

Веб-сервер SHALL предоставлять следующие HTTP API endpoints:

**POST /update_from_cs**
- Назначение: получение обновлений о текущем треке от C# компонента MediaMonitor
- Формат данных: JSON
- Обязательные поля: artist, title, position, duration, is_playing, cover_version, status
- Действие: обновление глобального состояния current_data и рассылка обновлений всем подключенным WebSocket клиентам
- Код ответа: 200 OK при успешной обработке

**GET /cover**
- Назначение: получение изображения обложки текущего трека
- Параметры: v (версия обложки для обхода кэша браузера)
- Формат ответа: бинарные данные изображения (image/png)
- Заголовки: Cache-Control для управления кэшированием
- Код ответа: 200 OK при наличии обложки, 404 Not Found при отсутствии

**GET /ws**
- Назначение: установка WebSocket соединения для real-time обновлений
- Протокол: WebSocket (RFC 6455)
- Типы сообщений: init (начальное состояние), update (обновление данных), config_update (изменение конфигурации)
- Формат данных: JSON
- Поддержка: неограниченное количество одновременных соединений

**POST /update_config**
- Назначение: обновление конфигурации системы
- Формат данных: JSON с параметрами конфигурации
- Действие: сохранение в файл config.json и уведомление всех WebSocket клиентов
- Код ответа: 200 OK при успешном обновлении

**GET /sources**
- Назначение: получение списка доступных источников обложек и их статуса
- Формат ответа: JSON массив с информацией об источниках
- Код ответа: 200 OK

**GET /{template}.html**
- Назначение: статическая раздача HTML файлов шаблонов визуализации
- Поддерживаемые шаблоны: visualisation.html, visualisation_var2.html, visualisation_var3.html, visualisation_horizontal.html
- Формат ответа: text/html
- Код ответа: 200 OK при наличии файла, 404 Not Found при отсутствии

Веб-сервер SHALL поддерживать WebSocket протокол для обеспечения двунаправленной real-time коммуникации с клиентами. При установке WebSocket соединения сервер SHALL немедленно отправлять текущее состояние системы (тип сообщения "init"). При изменении данных о треке или конфигурации сервер SHALL автоматически рассылать обновления всем подключенным клиентам.

Система SHALL реализовать троттлинг WebSocket обновлений с минимальным интервалом 100 миллисекунд между сообщениями для предотвращения перегрузки клиентов при частых изменениях позиции воспроизведения. Сервер SHALL автоматически очищать неактивные WebSocket соединения и корректно обрабатывать отключение клиентов.

Технические характеристики веб-сервера:
- Время отклика API: менее 10 миллисекунд
- Задержка WebSocket обновлений: менее 100 миллисекунд
- Максимальное количество одновременных соединений: ограничено только системными ресурсами
- Поддержка CORS: не требуется (работа только на localhost)
- Graceful shutdown: корректное завершение всех соединений при остановке

#### 4.1.5. Визуализация треков

Система SHALL предоставлять четыре профессиональных шаблона визуализации информации о текущем треке, каждый из которых оптимизирован для различных сценариев использования:

Визуальные эффекты, которые SHALL поддерживать система:

- **Wave Visualizer**: анимированный волновой визуализатор, синхронизированный с воспроизведением

#### 4.1.8. Интеграция C# и Python компонентов

Система SHALL обеспечивать бесшовную интеграцию между C# компонентом мониторинга медиаплееров (MediaMonitor) и Python веб-сервером через HTTP протокол с использованием JSON формата данных.

**Архитектура взаимодействия:**

C# компонент MediaMonitor SHALL работать как отдельный процесс (MediaMonitor.exe), выполняющий следующие функции:
- Мониторинг медиаплееров через Windows Media Control API с частотой 1 секунда
- Обнаружение смены треков путем сравнения текущих artist/title с предыдущими значениями
- Загрузка обложки альбома через Thumbnail API при смене трека
- Формирование JSON объекта с актуальными данными о треке
- Отправка HTTP POST запроса на Python сервер

Python веб-сервер SHALL принимать данные от C# компонента через endpoint POST /update_from_cs и выполнять следующие действия:
- Парсинг JSON данных из тела запроса
- Обновление глобального состояния current_data
- Валидация полученных данных
- Рассылка обновлений всем подключенным WebSocket клиентам
- Возврат HTTP ответа с кодом 200 OK

**Формат JSON данных:**

C# компонент SHALL отправлять данные в следующем формате:
```json
{
    "artist": "string",
    "title": "string",
    "position": 0.0,
    "duration": 0.0,
    "is_playing": true,
    "cover_version": 1,
    "status": "active"
}
```

Все строковые поля SHALL использовать кодировку UTF-8. Числовые поля position и duration SHALL быть представлены в секундах с точностью до одного знака после запятой. Поле cover_version SHALL инкрементироваться при каждой смене трека для обеспечения обновления обложки в браузере. Поле status SHALL принимать значения "active" (есть активная медиа-сессия) или "inactive" (нет активной медиа-сессии).

**Обработка ошибок и восстановление:**

Система SHALL реализовать механизмы обработки ошибок и автоматического восстановления соединения:

C# компонент SHALL:
- Автоматически переподключаться к Python серверу при разрыве соединения с интервалом повторных попыток 5 секунд
- Логировать ошибки HTTP запросов для диагностики
- Продолжать мониторинг медиаплееров даже при недоступности Python сервера
- Буферизовать последнее состояние для отправки при восстановлении соединения

Python сервер SHALL:
- Корректно обрабатывать некорректные JSON данные с возвратом HTTP 400 Bad Request
- Валидировать наличие обязательных полей в запросе
- Логировать ошибки парсинга и валидации
- Продолжать работу при получении некорректных данных без критических сбоев

**Управление жизненным циклом:**

Desktop-приложение SHALL автоматически запускать C# компонент MediaMonitor при нажатии кнопки START (если не используется встроенный Python мониторинг). При остановке сервера или закрытии приложения система SHALL корректно завершать процесс MediaMonitor.exe.

Система SHALL поддерживать гибридный режим работы, при котором одновременно могут работать C# и Python компоненты мониторинга для целей отладки и сравнения производительности.

- Проверка корректности цветовых значений (RGB, RGBA, HEX форматы)
- Валидация диапазонов числовых параметров
- Проверка существования выбранного шаблона визуализации
- Проверка корректности значений align_items и justify_content

**Резервное копирование:**

Система MAY создавать резервную копию конфигурационного файла (config.json.backup) перед сохранением изменений для возможности восстановления предыдущих настроек в случае ошибки.

### 4.2. Требования к надёжности

Требования к надёжности определяют способность системы NowPlay стабильно функционировать в различных условиях эксплуатации, корректно обрабатывать ошибочные ситуации и автоматически восстанавливаться после сбоев.

#### 4.2.1. Обработка ошибок подключения к медиаплеерам

Система SHALL корректно обрабатывать отсутствие активных медиаплееров на компьютере пользователя без критических сбоев или зависаний. При отсутствии активной медиа-сессии компонент мониторинга SHALL отправлять статус "inactive" на веб-сервер, который SHALL передавать это состояние всем подключенным клиентам.

Веб-виджеты SHALL отображать соответствующее сообщение при статусе "inactive", например "Ожидание воспроизведения..." или "Медиаплеер не активен", вместо попытки отобразить несуществующие данные о треке. Система SHALL автоматически возобновлять нормальную работу при появлении активной медиа-сессии без необходимости перезапуска.

При потере доступа к медиаплееру во время воспроизведения (например, при аварийном завершении медиаплеера) система SHALL:
- Обнаружить отсутствие медиа-сессии при следующем опросе (в течение 1 секунды)
- Отправить статус "inactive" на сервер
- Сохранить последнюю известную информацию о треке для возможного отображения
- Продолжать мониторинг для обнаружения новой медиа-сессии

Система SHALL логировать события потери и восстановления соединения с медиаплеерами для диагностики проблем. Логи SHALL содержать временные метки и описание события без чувствительной информации.

#### 4.2.2. Стабильность веб-сервера

Веб-сервер SHALL обеспечивать непрерывную работу минимум 24 часа без перезапуска при нормальных условиях эксплуатации. Система SHALL корректно обрабатывать длительные стриминговые сессии продолжительностью 48 часов и более без деградации производительности или утечек памяти.

Сервер SHALL автоматически восстанавливаться после некритических ошибок, таких как:
- Ошибки парсинга некорректных JSON данных от клиентов
- Разрыв WebSocket соединений
- Ошибки чтения файлов (обложки, конфигурация)
- Временная недоступность сетевых ресурсов

При возникновении критической ошибки, которая не может быть обработана автоматически, сервер SHALL:
- Логировать полную информацию об ошибке, включая stack trace
- Попытаться корректно завершить все активные соединения
- Уведомить пользователя через GUI о необходимости перезапуска
- Сохранить текущее состояние конфигурации

Система SHALL реализовать graceful shutdown при остановке сервера:
- Завершение приема новых соединений
- Отправка уведомлений о закрытии всем WebSocket клиентам
- Ожидание завершения обработки текущих запросов (таймаут 5 секунд)
- Корректное освобождение всех ресурсов (сокеты, файлы, память)
- Сохранение конфигурации и состояния

Сервер SHALL автоматически очищать неактивные WebSocket соединения для предотвращения накопления "мертвых" соединений. Проверка активности SHALL выполняться при каждой попытке отправки данных, и неактивные соединения SHALL удаляться из списка listeners.

#### 4.2.3. Надёжность получения обложек

Система SHALL реализовать надежный механизм получения обложек альбомов с использованием fallback-стратегии при недоступности источников. При неудаче получения обложки из источника с более высоким приоритетом система SHALL автоматически переключаться на следующий источник в иерархии без вмешательства пользователя.

Система SHALL обрабатывать следующие ошибочные ситуации при загрузке обложек:
- **Timeout**: если запрос к API источника не завершается в течение 3 секунд, система SHALL прервать запрос и перейти к следующему источнику
- **HTTP 404 Not Found**: если источник не содержит обложку для данного трека, система SHALL немедленно перейти к следующему источнику без повторных попыток
- **HTTP 5xx Server Error**: при ошибке на стороне сервера источника система SHALL перейти к следующему источнику
- **Network Error**: при отсутствии интернет-соединения или недоступности источника система SHALL перейти к следующему источнику
- **Invalid Image Data**: если полученные данные не являются корректным изображением, система SHALL перейти к следующему источнику

Если все источники недоступны или не содержат обложку для данного трека, система SHALL использовать дефолтную обложку (songinfo/NoCover.png), которая SHALL всегда присутствовать в системе. Дефолтная обложка SHALL иметь нейтральный дизайн, подходящий для любого контента.

Система SHALL кэшировать успешно загруженные обложки локально для предотвращения повторных запросов к API при воспроизведении того же трека. Кэш SHALL сохраняться между сессиями работы приложения. При смене трека система SHALL проверять наличие обложки в кэше перед обращением к внешним источникам.

Система SHALL логировать все попытки загрузки обложек, включая использованный источник, результат (успех/ошибка) и время выполнения запроса. Эта информация SHALL использоваться для диагностики проблем с источниками и оптимизации приоритизации.

#### 4.2.4. Синхронизация C# и Python компонентов

Система SHALL обеспечивать надежную синхронизацию между C# компонентом MediaMonitor и Python веб-сервером с автоматическим переподключением при разрыве соединения.

C# компонент SHALL реализовать механизм автоматического переподключения:
- При неудаче HTTP POST запроса к Python серверу компонент SHALL повторить попытку через 5 секунд
- Количество попыток переподключения SHALL быть неограниченным
- Компонент SHALL продолжать мониторинг медиаплееров даже при недоступности сервера
- При восстановлении соединения компонент SHALL немедленно отправить текущее состояние

Python сервер SHALL корректно обрабатывать ситуации, когда C# компонент временно недоступен:
- Сервер SHALL продолжать работу и обслуживание WebSocket клиентов
- При отсутствии обновлений от C# компонента сервер SHALL сохранять последнее известное состояние
- Сервер SHALL автоматически принимать новые данные при восстановлении соединения с C# компонентом

Система SHALL обеспечивать согласованность данных между компонентами:
- Каждое обновление от C# компонента SHALL содержать полный набор данных о текущем состоянии
- Python сервер SHALL атомарно обновлять глобальное состояние current_data
- WebSocket клиенты SHALL получать только согласованные обновления

При запуске системы SHALL выполняться проверка доступности обоих компонентов:
- Desktop-приложение SHALL проверять наличие исполняемого файла MediaMonitor.exe
- При запуске сервера SHALL выполняться проверка доступности порта 80
- Пользователь SHALL получать уведомление о проблемах с запуском компонентов

#### 4.2.5. Обработка некорректных данных

Система SHALL выполнять валидацию всех входных данных для предотвращения ошибок и обеспечения стабильной работы. Валидация SHALL применяться на всех уровнях системы: при получении данных от C# компонента, при обработке запросов от клиентов и при загрузке конфигурации.

**Валидация данных от C# компонента:**

Python сервер SHALL проверять данные, полученные через POST /update_from_cs:
- Наличие всех обязательных полей (artist, title, position, duration, is_playing, cover_version, status)
- Корректность типов данных (строки для текстовых полей, числа для числовых, булево для is_playing)
- Валидность значений (position <= duration, cover_version >= 0, status in ["active", "inactive"])
- Корректность кодировки UTF-8 для текстовых полей

При обнаружении некорректных данных сервер SHALL:
- Возвращать HTTP 400 Bad Request с описанием ошибки
- Логировать попытку отправки некорректных данных
- Сохранять предыдущее корректное состояние
- Не рассылать некорректные данные WebSocket клиентам

**Валидация конфигурации:**

Система SHALL валидировать параметры конфигурации при загрузке из config.json и при получении обновлений через POST /update_config:
- Проверка корректности цветовых значений (соответствие форматам RGB, RGBA, HEX)
- Валидация булевых параметров (wave_enabled, ambient_light_enabled, auto_colors)
- Проверка существования выбранного шаблона визуализации
- Валидация значений позиционирования (align_items, justify_content)

При обнаружении некорректных значений система SHALL автоматически заменять их на значения по умолчанию и логировать предупреждение.

**Защита от инъекций:**

Система SHALL защищаться от потенциальных атак через инъекции:
- Все данные, отображаемые в веб-виджетах, SHALL быть экранированы для предотвращения XSS атак
- JSON данные SHALL парситься с использованием безопасных библиотек
- Пути к файлам SHALL валидироваться для предотвращения path traversal атак
- Размер входных данных SHALL быть ограничен разумными пределами

**Обработка специальных символов:**

Система SHALL корректно обрабатывать специальные символы в метаданных треков:
- Unicode символы (кириллица, иероглифы, эмодзи)
- HTML специальные символы (<, >, &, ", ')
- Управляющие символы (переводы строк, табуляция)
- Нулевые байты и другие потенциально опасные символы

Все текстовые данные SHALL быть санитизированы перед отображением в GUI и веб-виджетах для предотвращения проблем с рендерингом и безопасностью.

#### 4.2.6. Управление памятью

Система SHALL обеспечивать эффективное управление памятью для предотвращения утечек и обеспечения стабильной работы при длительной эксплуатации.

**Требования к использованию памяти:**
- Python компонент (веб-сервер + GUI): не более 150 МБ RAM
- C# компонент (MediaMonitor): не более 50 МБ RAM
- Общее использование памяти: не более 200 МБ RAM
- Отсутствие роста потребления памяти при длительной работе (24+ часа)

Система SHALL реализовать следующие механизмы управления памятью:

**Кэширование с ограничениями:**
- Кэш обложек SHALL иметь ограничение по размеру (например, максимум 100 обложек)
- При достижении лимита SHALL удаляться наиболее старые записи (LRU стратегия)
- Кэш цветовых палитр SHALL автоматически очищаться при смене трека
- Размер кэша SHALL быть настраиваемым через конфигурацию

**Управление WebSocket соединениями:**
- Неактивные соединения SHALL автоматически удаляться из списка listeners
- Буферы отправки SHALL иметь ограничение по размеру
- При закрытии соединения все связанные ресурсы SHALL немедленно освобождаться

**Оптимизация обработки изображений:**
- Обложки SHALL масштабироваться до оптимального размера (600x600) перед сохранением
- Canvas для извлечения цветов SHALL использовать уменьшенный размер (80x80)
- Временные объекты SHALL удаляться после завершения обработки

**Мониторинг использования памяти:**
- Система MAY логировать текущее использование памяти периодически
- При превышении пороговых значений SHALL выводиться предупреждение
- Система MAY предоставлять статистику использования памяти в GUI

Система SHALL проходить тестирование на отсутствие утечек памяти при длительной работе (48+ часов) с периодической сменой треков (минимум 1000 смен треков).

#### 4.2.7. Логирование ошибок

Система SHALL реализовать комплексное логирование для диагностики проблем и мониторинга работы системы. Логи SHALL записываться в файлы с ротацией для предотвращения неограниченного роста размера.

**Уровни логирования:**

Система SHALL поддерживать следующие уровни логирования:
- **ERROR**: критические ошибки, требующие внимания (сбои компонентов, недоступность ресурсов)
- **WARNING**: предупреждения о потенциальных проблемах (недоступность источника обложек, некорректные данные)
- **INFO**: информационные сообщения о нормальной работе (запуск/остановка сервера, смена треков)
- **DEBUG**: детальная информация для отладки (доступна только в режиме разработки)

**Содержание логов:**

Каждая запись в логе SHALL содержать:
- Временную метку в формате ISO 8601 (YYYY-MM-DD HH:MM:SS.mmm)
- Уровень логирования
- Имя компонента (MediaMonitor, WebServer, GUI, CoverFetcher)
- Описание события или ошибки
- Дополнительный контекст (stack trace для ошибок, параметры запросов)

**Логируемые события:**

Система SHALL логировать следующие типы событий:

*Критические ошибки (ERROR):*
- Невозможность запуска веб-сервера (порт занят, недостаточно прав)
- Критические ошибки в C# компоненте
- Ошибки чтения/записи конфигурационного файла
- Необработанные исключения в основных компонентах

*Предупреждения (WARNING):*
- Недоступность источников обложек
- Получение некорректных данных от клиентов
- Превышение пороговых значений использования ресурсов
- Некорректные значения в конфигурации

*Информационные сообщения (INFO):*
- Запуск и остановка веб-сервера
- Запуск и остановка C# компонента
- Смена треков с указанием исполнителя и названия
- Подключение и отключение WebSocket клиентов
- Успешная загрузка обложек с указанием источника

**Управление логами:**

Система SHALL реализовать ротацию лог-файлов:
- Максимальный размер одного лог-файла: 10 МБ
- Количество хранимых файлов: 5
- При достижении лимита размера создается новый файл, старые файлы удаляются
- Имена файлов: nowplay.log, nowplay.log.1, nowplay.log.2, и т.д.

Логи SHALL храниться в папке logs/ в корне проекта. Система SHALL автоматически создавать эту папку при первом запуске, если она не существует.

**Конфиденциальность:**

Логи SHALL NOT содержать чувствительную информацию:
- Пароли или токены доступа к API
- Персональные данные пользователей
- Полные пути к файлам (только относительные пути)
- IP адреса (кроме localhost)

Пользователь SHALL иметь возможность просматривать логи через GUI (опционально) или непосредственно открывая файлы в текстовом редакторе.

### 4.3. Требования к производительности

Требования к производительности определяют количественные характеристики работы системы NowPlay, обеспечивающие эффективное использование системных ресурсов и быстрый отклик на действия пользователя. Все указанные значения являются обязательными для выполнения и SHALL быть подтверждены результатами тестирования.

#### 4.3.1. Время реакции на смену трека

Система SHALL обнаруживать смену трека и обновлять отображаемую информацию не более чем за 2 секунды с момента фактического переключения трека в медиаплеере. Этот интервал включает:
- Обнаружение смены трека C# компонентом (максимум 1 секунда - частота опроса)
- Загрузка обложки альбома (параллельно с отправкой данных)
- Отправка данных на Python сервер (менее 10 миллисекунд)
- Рассылка обновлений WebSocket клиентам (менее 100 миллисекунд)
- Обновление отображения в веб-виджете (менее 100 миллисекунд)

В оптимальных условиях (обложка уже в кэше, стабильное соединение) время реакции SHALL составлять менее 1.5 секунды. Система SHALL обновлять текстовую информацию о треке (исполнитель, название) немедленно, не дожидаясь завершения загрузки обложки.

Измерение времени реакции SHALL выполняться от момента смены трека в медиаплеере до момента отображения новой информации в веб-виджете. Тестирование SHALL проводиться с различными медиаплеерами (Spotify, VLC, Chrome) для подтверждения соответствия требованию.

#### 4.3.2. Загрузка обложек альбомов

Система SHALL загружать обложки альбомов не более чем за 3 секунды при наличии стабильного интернет-соединения со скоростью минимум 1 Мбит/с. Это время включает:
- Запрос к API источника обложек (Last.fm, iTunes, Yandex, VK)
- Получение URL изображения или бинарных данных
- Загрузка изображения
- Сохранение в локальный файл songinfo/cover.png
- Масштабирование до оптимального размера (если требуется)

При использовании кэшированной обложки (трек воспроизводился ранее) время доступа SHALL составлять менее 100 миллисекунд, так как обложка читается из локального файла без сетевых запросов.

Система SHALL реализовать таймаут 3 секунды для каждого источника обложек. Если источник не отвечает в течение этого времени, система SHALL немедленно переключаться на следующий источник в иерархии приоритетов. Общее время попыток получения обложки из всех источников SHALL NOT превышать 10 секунд, после чего SHALL использоваться дефолтная обложка.

Загрузка обложки SHALL выполняться асинхронно и параллельно с обновлением текстовой информации о треке, чтобы не блокировать отображение исполнителя и названия. Пользователь SHALL видеть обновленную текстовую информацию немедленно, а обложка SHALL появляться по мере загрузки.

#### 4.3.3. Нагрузка на центральный процессор (CPU)

Система SHALL обеспечивать минимальную нагрузку на CPU для предотвращения влияния на производительность стриминга и игр. Требования к нагрузке CPU SHALL быть следующими:

**При переключении треков:**
- Максимальная нагрузка: не более 2% CPU
- Средняя нагрузка: 0.8-1.5% CPU
- Длительность пиковой нагрузки: не более 500 миллисекунд
- Компоненты, создающие нагрузку: загрузка обложки, извлечение цветов, обновление GUI

**В режиме ожидания (трек воспроизводится, нет изменений):**
- Максимальная нагрузка: не более 0.5% CPU
- Средняя нагрузка: 0.1-0.3% CPU
- Компоненты, создающие нагрузку: мониторинг медиаплееров (1 раз в секунду), обновление позиции воспроизведения

**При отсутствии активного медиаплеера:**
- Максимальная нагрузка: не более 0.3% CPU
- Средняя нагрузка: менее 0.1% CPU
- Компоненты, создающие нагрузку: только мониторинг наличия медиа-сессии

Измерение нагрузки CPU SHALL выполняться на референсной системе (Intel Core i5 или AMD Ryzen 5, 4 ядра, 3.0 GHz) с использованием стандартных инструментов мониторинга (Task Manager, Process Explorer). Тестирование SHALL проводиться при различных сценариях использования:
- Быстрое переключение треков (каждые 10 секунд)
- Нормальное воспроизведение (треки по 3-5 минут)
- Длительная работа без смены треков (30+ минут)

Система SHALL использовать оптимизированные алгоритмы для минимизации нагрузки на CPU:
- Уменьшенный размер canvas для извлечения цветов (80x80 пикселей вместо 200x200)
- Увеличенный шаг выборки пикселей (128 байт вместо 32)
- Кэширование результатов извлечения цветов
- Дебаунсинг обновлений позиции воспроизведения (минимум 100ms между обновлениями)
- Асинхронная обработка всех операций ввода-вывода

Нагрузка на CPU SHALL оставаться стабильной при длительной работе системы (24+ часа) без деградации производительности. Система SHALL NOT создавать фоновые процессы или потоки, которые постоянно потребляют CPU в режиме ожидания.

#### 4.3.4. Использование оперативной памяти (RAM)

Система SHALL эффективно использовать оперативную память для обеспечения возможности работы на системах с ограниченными ресурсами. Требования к использованию памяти SHALL быть следующими:

**Python компонент (веб-сервер + GUI):**
- Максимальное использование: не более 150 МБ RAM
- Типичное использование: 80-120 МБ RAM
- Использование при запуске: 60-80 МБ RAM
- Рост при длительной работе: не более 10% от начального значения за 24 часа

**C# компонент (MediaMonitor):**
- Максимальное использование: не более 50 МБ RAM
- Типичное использование: 20-35 МБ RAM
- Использование при запуске: 15-20 МБ RAM
- Рост при длительной работе: не более 5% от начального значения за 24 часа

**Общее использование памяти:**
- Максимальное: не более 200 МБ RAM для всей системы
- Типичное: 100-155 МБ RAM
- Дополнительная память для кэша обложек: до 50 МБ (зависит от количества кэшированных обложек)

Система SHALL NOT иметь утечек памяти при длительной работе. Тестирование на утечки памяти SHALL проводиться в течение минимум 48 часов с периодической сменой треков (минимум 1000 смен). Использование памяти SHALL оставаться стабильным с допустимым ростом не более 15% от начального значения.

Система SHALL реализовать эффективное управление памятью:
- Ограничение размера кэша обложек (максимум 100 обложек)
- Автоматическая очистка неиспользуемых ресурсов
- Использование генераторов вместо списков для больших объемов данных (Python)
- Своевременное освобождение ресурсов при закрытии соединений

Измерение использования памяти SHALL выполняться с использованием стандартных инструментов мониторинга (Task Manager, Process Explorer, Resource Monitor) на референсной системе с 8 ГБ RAM.

#### 4.3.5. Троттлинг обновлений

Система SHALL реализовать троттлинг (ограничение частоты) WebSocket обновлений для предотвращения перегрузки клиентов и сети при частых изменениях данных. Минимальный интервал между WebSocket сообщениями SHALL составлять 100 миллисекунд.

Троттлинг SHALL применяться к следующим типам обновлений:
- Изменение позиции воспроизведения (position) - обновляется каждую секунду C# компонентом, но рассылается клиентам не чаще чем раз в 100ms
- Изменение статуса воспроизведения (is_playing) - немедленная рассылка без троттлинга
- Смена трека - немедленная рассылка без троттлинга
- Обновление конфигурации - немедленная рассылка без троттлинга

Механизм троттлинга SHALL работать следующим образом:
1. При получении обновления от C# компонента сервер проверяет время последней рассылки
2. Если прошло менее 100ms с момента последней рассылки, обновление буферизируется
3. По истечении 100ms буферизованное обновление отправляется всем клиентам
4. Если за время ожидания поступило несколько обновлений, отправляется только последнее

Троттлинг SHALL обеспечивать:
- Снижение нагрузки на сеть при частых обновлениях позиции
- Предотвращение перегрузки браузера обновлениями
- Плавную анимацию прогресс-бара без рывков
- Немедленное обновление критически важной информации (смена трека)

Система SHALL NOT применять троттлинг к обновлениям, требующим немедленной реакции (смена трека, изменение статуса воспроизведения), чтобы обеспечить быстрый отклик пользовательского интерфейса.

#### 4.3.6. Время запуска приложения

Desktop-приложение SHALL запускаться не более чем за 5 секунд с момента запуска исполняемого файла до полной готовности к работе. Время запуска включает:
- Инициализацию Python интерпретатора и загрузку модулей (1-2 секунды)
- Создание GUI и отрисовку главного окна (0.5-1 секунда)
- Загрузку конфигурации из config.json (менее 0.1 секунды)
- Инициализацию компонентов системы (менее 0.5 секунды)
- Отображение готового к использованию интерфейса

На системах с SSD время запуска SHALL составлять 2-3 секунды. На системах с HDD допускается время запуска до 5 секунд. Система SHALL отображать splash screen или индикатор загрузки во время запуска для информирования пользователя о процессе инициализации.

Веб-сервер SHALL запускаться не более чем за 2 секунды после нажатия кнопки START в GUI. Это время включает:
- Инициализацию aiohttp приложения (менее 0.5 секунды)
- Привязку к порту 80 (менее 0.1 секунды)
- Запуск C# компонента MediaMonitor (0.5-1 секунда)
- Установку соединения между компонентами (менее 0.5 секунды)

Пользователь SHALL получать визуальное подтверждение успешного запуска сервера (изменение цвета индикатора, текстовое сообщение) немедленно после завершения инициализации.

#### 4.3.7. Задержка обновлений в веб-виджете

Задержка обновления информации в веб-виджете SHALL составлять не более 500 миллисекунд с момента получения данных сервером до отображения в браузере. Эта задержка включает:
- Обработку данных на сервере (менее 10 миллисекунд)
- Отправку WebSocket сообщения (менее 50 миллисекунд на localhost)
- Обработку сообщения в JavaScript (менее 10 миллисекунд)
- Обновление DOM и применение CSS transitions (менее 100 миллисекунд)
- Извлечение цветов из обложки при включенной опции auto_colors (менее 300 миллисекунд)

В оптимальных условиях (без извлечения цветов, быстрая система) задержка SHALL составлять менее 100 миллисекунд, обеспечивая практически мгновенное обновление информации.

Система SHALL обеспечивать плавные анимации переходов без рывков и задержек:
- CSS transitions SHALL иметь длительность 300 миллисекунд
- Анимация прогресс-бара SHALL обновляться плавно с использованием requestAnimationFrame
- Смена обложки SHALL сопровождаться fade-in/fade-out эффектом

Веб-виджеты SHALL оставаться отзывчивыми при любой нагрузке на систему. Обновления SHALL NOT блокировать основной поток браузера и SHALL NOT вызывать "замораживание" интерфейса.

Тестирование задержки обновлений SHALL проводиться с использованием инструментов разработчика браузера (Performance tab, Network tab) для измерения времени обработки WebSocket сообщений и обновления DOM.

**Плавные анимации:**

**Темная тема по умолчанию:**

**Визуальные эффекты:**
- Тени: мягкие тени для создания глубины (box-shadow)

- Прозрачность: использование rgba для полупрозрачных элементов

**Доступность:**
- Контрастность текста: минимум 4.5:1 для нормального текста, 3:1 для крупного текста

- Поддержка клавиатурной навигации: все элементы SHALL быть доступны через Tab

- Tooltips SHALL автоматически скрываться при уходе курсора

**Вариант 2: Запуск из исходного кода (для разработчиков и продвинутых пользователей)**

1. Установка Python 3.12 или выше с официального сайта python.org
2. Установка .NET 6.0 SDK или Runtime с официального сайта Microsoft
3. Клонирование репозитория: `git clone https://github.com/username/NowPlay.git`
4. Переход в папку проекта: `cd NowPlay`
5. Создание виртуального окружения: `python -m venv .venv`
6. Активация виртуального окружения:
   - Windows: `.venv\Scripts\activate`
7. Установка зависимостей: `pip install -r requirements.txt`
8. Компиляция C# компонента:
   - Переход в папку MediaMonitor: `cd MediaMonitor`
   - Компиляция: `dotnet build -c Release`
9. Запуск приложения: `python main.py`

Система SHALL предоставлять подробную документацию по установке в файле README.md с пошаговыми инструкциями и скриншотами.

#### 4.7.2. Порядок запуска и использования

**Первый запуск:**

1. Запуск desktop-приложения через ярлык на рабочем столе или меню "Пуск"
2. Ознакомление с интерфейсом на странице Start
3. Опциональная настройка параметров на странице Settings (цвета, шаблон, эффекты)
4. Нажатие кнопки START для запуска веб-сервера
5. Автоматический запуск C# компонента MediaMonitor
6. Ожидание появления индикатора "Сервер запущен" (зеленый цвет)

**Интеграция с OBS Studio:**

1. Открытие OBS Studio
2. Создание новой сцены или выбор существующей
3. Добавление нового источника: Источники → + → Browser (Browser Source)
4. Настройка Browser Source:
   - Имя: "NowPlay Widget" (или любое другое)
   - URL: копирование ссылки из приложения NowPlay (кнопка "Копировать ссылку")
   - Ширина и высота: в зависимости от выбранного шаблона (указаны в приложении)
   - Галочка "Shutdown source when not visible": рекомендуется отключить
   - Галочка "Refresh browser when scene becomes active": опционально
5. Нажатие "OK" для добавления источника
6. Позиционирование и масштабирование виджета в сцене OBS
7. Проверка работы: запуск музыки в любом медиаплеере

Виджет SHALL автоматически обновляться при смене треков без необходимости перезагрузки источника в OBS.

**Ежедневное использование:**

1. Запуск desktop-приложения NowPlay
2. Нажатие кнопки START (если сервер не запущен автоматически)
3. Запуск медиаплеера и воспроизведение музыки
4. Автоматическое отображение информации о треке в виджете OBS
5. Опциональная настройка параметров в реальном времени через страницу Settings
6. Остановка сервера кнопкой STOP при завершении работы (опционально)

Система SHALL сохранять все настройки между сессиями, поэтому повторная настройка не требуется.
