# Оптимизация CPU MediaMonitor

## Проблема
Профилирование показало, что основная нагрузка CPU (6.35%) приходится на `system.private.corelib.dll` в категории "Сетевые подключения" - HTTP-запросы к Python серверу.

## Реализованные оптимизации

### 1. HTTP Семафор (Критично)
- **Проблема**: Параллельные HTTP-запросы создавали избыточную нагрузку
- **Решение**: Добавлен `httpSemaphore` для ограничения до 1 одновременного запроса
- **Эффект**: Устранение race conditions и снижение нагрузки на сетевой стек

### 2. Батчинг HTTP-запросов (Критично)
- **Проблема**: Debounce 100мс приводил к слишком частым обновлениям
- **Решение**: 
  - Увеличен debounce до 500мс
  - Добавлен cooldown 2 секунды между HTTP-запросами (`UPDATE_COOLDOWN_SECONDS`)
- **Эффект**: Снижение частоты HTTP-запросов в ~20 раз

### 3. Кеширование источников (Критично)
- **Проблема**: `SendAvailableSources()` вызывался при каждом `LoadSelectedSource()`
- **Решение**: Кеширование на 30 секунд (`SOURCE_CACHE_SECONDS`)
- **Эффект**: Снижение перечисления сессий на 95%

### 4. Правильная обработка HTTP-ответов
- **Проблема**: Ответы не диспозились должным образом
- **Решение**: `using var response` для всех HTTP-запросов
- **Эффект**: Устранение утечек HttpResponseMessage

### 5. Таймаут HttpClient
- **Проблема**: Отсутствие глобального таймаута
- **Решение**: `HttpClient.Timeout = 5 секунд` в конструкторе
- **Эффект**: Предотвращение зависаний при недоступности сервера

### 6. ConfigureAwait для .NET операций
- **Проблема**: Захват контекста синхронизации
- **Решение**: `.ConfigureAwait(false)` на всех .NET async операциях (не WinRT)
- **Эффект**: Снижение overhead на переключение контекста

## Технические детали

### Новые поля
```csharp
private readonly SemaphoreSlim httpSemaphore = new SemaphoreSlim(1, 1);
private DateTime lastHttpUpdate = DateTime.MinValue;
private const double UPDATE_COOLDOWN_SECONDS = 2.0;
private DateTime lastSourceEnumeration = DateTime.MinValue;
private const int SOURCE_CACHE_SECONDS = 30;
```

### Важное замечание о WinRT объектах
`GlobalSystemMediaTransportControlsSession` - это WinRT объект, который **не требует** явного вызова `Dispose()`. Попытка вызвать `Dispose()` приводит к ошибке компиляции. WinRT использует автоматическое управление памятью через COM reference counting.

## Ожидаемый результат

**До оптимизации:**
- HTTP нагрузка: ~6.35% CPU
- Частота запросов: ~10-20 в секунду при активном воспроизведении

**После оптимизации:**
- HTTP нагрузка: ~0.5-1% CPU (снижение в 6-12 раз)
- Частота запросов: максимум 0.5 в секунду (1 раз в 2 секунды)
- Перечисление источников: 1 раз в 30 секунд вместо постоянного

## Тестирование

Запустите MediaMonitor и проверьте:
1. CPU usage должен быть стабильным (~1-2%)
2. В консоли не должно быть частых HTTP-ошибок
3. Обновления треков работают корректно (с задержкой до 500мс)

```bash
dotnet run --project MediaMonitor/MediaMonitor.csproj
```

Для длительного теста стабильности:
```bash
python MediaMonitor/test_cpu_stability.py
```
